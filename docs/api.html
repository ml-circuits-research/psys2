API, CLI, sessions

Status: implemented planned (vision only) Sessions, worlds, memory and the CLI are implemented; job, journal and deployment endpoints are vision only.

Specs: spec 06 Dialog, server, webchat

Vision: vision §14

Purpose

How clients reach C2: an HTTP API served by node:http (no framework), a CLI, and in-memory sessions. Everything is JSON except the memory dump. No LLM is reachable from the server process.

Implemented endpoints (spec 06)

node src/server/index.mjs [--port 8080]

Method and pathBehaviour
GET /v1/health{ ok, version, worlds }
GET /v1/worldsworld manifests
GET /v1/worlds/{id}manifest, legend summary, tests summary
POST /v1/sessions{ language? } returns { sessionId }
POST /v1/sessions/{id}/messages{ text } returns the reply object
GET /v1/sessions/{id}/memorysession wires as SOP Lang (text/plain)
POST /v1/learn/*, POST /v1/worlds/{id}/improvements501 with a pointer to the vision (C1/C3 not implemented)

Example session

POST /v1/sessions
{ "language": "auto" }
-> { "sessionId": "s_1" }

POST /v1/sessions/s_1/messages
{ "text": "Tom has 5 apples. How many apples does Tom have?" }
-> { "text": "...", "lang": "en", "translation": null, "segments": [...],
     "wires": [...], "answers": [...], "statuses": ["supported"], "trace": {...} }

GET /v1/sessions/s_1/memory
-> text/plain: the session wires as SOP Lang

Sessions live in memory with a 30-minute idle timeout. The reply object is the one returned by session.send (C2 operation).

Webchat

A static page that runs C2 entirely in the browser, with no server, using the same src/ modules copied by scripts/build-webchat.mjs into docs/webchat/lib/ and worlds bundled into docs/webchat/worlds/. It shows the chat and, on demand, the trace. ES modules need HTTP, so file:// is not supported; GitHub Pages (/docs) or any static server works. Open the webchat demo.

Target API (vision §14)

planned (vision only) Everything below except the session endpoints.

Endpoint familyPurpose
POST /v1/sessions and /sessions/{id}/messagesSnapshot-pinned conversation and streamed results (the implemented subset has no snapshot pinning or streaming)
POST /v1/sessions/{id}/files and /v1/analysesTemporary file analysis and batch reports; no automatic world ingestion
POST /v1/learn/worlds and /v1/learn/filesCreate C1 jobs from scoped requests and registered sources
POST /v1/worlds/{id}/improvementsCreate C3 jobs; the scheduler uses the same job contract
GET /v1/jobs/{id}Stage, checkpoints, budget, evidence, outcome
GET /v1/worlds/{id}/versions and /journalCoverage, releases, learning history, dependencies
POST /v1/episodes/{id}/feedbackOptional feedback recorded as candidate evidence
POST /v1/deployments/{id}/rollbackPolicy-authorized atomic rollback to a compatible snapshot

Learning requests specify sources, target capabilities, allowed acquisition channels, language, time and GPU budgets, retention policy and desired assurance; competency questions may be supplied but hand-labeled circuits are not required. Every asynchronous API returns a job id and supports cancellation. Access control distinguishes reading, learning, deployment administration and external action execution.

Vision and specs differ

Spec 06 specifies only health, worlds, sessions, messages and memory, plus 501 stubs for learn and improvements. /files, /analyses, /jobs, /versions, /journal, /feedback and /rollback are in the vision but have no spec and are not served; /v1/worlds GET endpoints and /memory are spec-only additions.

Modules (vision §14)

ModuleResponsibility

Failure modes

  • Unknown session id or expired session (idle timeout): error response; the client creates a new session.
  • Learn or improvement endpoints: 501, not silently accepted.
  • Malformed JSON body: error response (not specified in detail by spec 06).
