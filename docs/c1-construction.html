C1 construction

Status: planned (vision only)

Specs: none (vision only)

Vision: vision §1, vision §9, vision §12

Purpose

C1 creates a world or a new foundational capability from source documents, a request and a budget. Coding agents use LLMs inside permitted skill steps; the platform runs skills, validates outputs and keeps release authority separate: C1 can only produce a candidate release, and an independent gate publishes. C1 is not implemented. The hand-built status=fixture worlds are not C1 output (ADR-001).

How a C1 job runs

  1. The job is admitted with explicit wall-time, GPU-time, memory and LLM-cost ceilings; missing ceilings fail admission, and every input role is bound to an immutable hash.
  2. Skills C1.01 to C1.08 run in order in a candidate workspace, each recording skill version, job id, source snapshot, parent artifacts, capabilities, model provider/version, prompt or hash (per retention policy), tool actions, cost, outputs and diagnostics. Artifacts are content-addressed; jobs are idempotent at a declared input manifest and resume from accepted checkpoints.
  3. Each skill has local acceptance checks that let an intermediate artifact proceed. The protected world-release gate is a separate step (Releases and journal).
  4. Error codes distinguish invalid input, exhausted budget, failed acceptance, infrastructure failure and cancellation, so a rejected candidate is not retried forever.

The job stays accountable to its original scope. A partial world can be published only with an explicitly narrower coverage manifest accepted by policy; the agent cannot quietly drop failed capabilities and declare the job complete. Unsupported capabilities create recorded follow-up work. One world failing must not block unrelated queued worlds, corrupt artifacts or force C2 onto an unaccepted candidate.

Skill manifest

The registry uses machine-readable manifests that declare artifact roles instead of filesystem paths. The vision shows C1.06 (JSON, not SOP Lang):

{
  "id": "c1.train_encoder", "version": "1.0.0",
  "inputs": ["legend", "backbone", "train_data", "dev_data", "recipe"],
  "outputs": ["adapter", "heads", "calibration", "training_report"],
  "capabilities": ["candidate.read", "candidate.write", "gpu.train"],
  "acceptance": ["data_integrity", "model_compatibility", "dev_metrics"],
  "retry": {"max_attempts": 3, "resume_checkpoint": true},
  "release_authority": false
}

C3.04 reuses this skill with a correction dossier and replay manifest as extra inputs. Each shipped skill needs instructions, input/output schemas, runner hooks, acceptance checks, recovery behavior and at least one fixture.

Worked example

Vision §12: a mechanics chapter and a request to support translational acceleration. The agent builds the legend, defines net force and mass, writes typed operations (mech.acceleration.v1 requires a body, positive mass, a net-force vector in a declared frame and compatible context), generates cases (multiple bodies, distractors, missing masses, resultant versus individual forces, unit changes, conditionals), creates the fine-tuning package and trains the adapter. Protected cases come from independent problem families.

Rules that bind C1

  • LLM annotations are draft labels, never operational facts. Knowledge-base ingestion goes through the accepted encoder and deterministic validators; external structured facts use a declared deterministic import with provenance.
  • An agent-authored acceptance test cannot replace a protected platform gate.
  • The agent cannot move the production pointer, change protected sets or weaken policy.

Failure modes

  • Budget exhausted, invalid input, failed acceptance, infrastructure failure, cancellation: distinct codes; no infinite retry.
  • Capability that cannot be built: recorded follow-up, never silently removed.
  • Candidate that fails the gate: stays inspectable, never active.
