C3 improvement

Status: planned (vision only)

Specs: none (vision only)

Vision: vision §10, vision §12, vision §11

Purpose

C3 improves an existing world from episodes, source changes, monitoring and optional feedback. It uses the same coding-agent and GPU infrastructure and the same candidate and release gates as C1. Its distinct duty is to explain a change in terms of observed behavior, preserve previous capabilities and decide whether new evidence supports a correction. A new world or a shared-foundation change becomes a linked C1 job or a coordinated release. C3 is not implemented (the server answers 501 on the improvement endpoint).

Triggers

The scheduler runs C3 after configurable intervals or on triggers: repeated unsupported questions, elevated rejection rates, a changed source, execution failures, drift. It applies deduplication, per-world budgets, retry limits and backoff. A blocked job records its reason and does not widen its permissions.

When evidence is insufficient

C3 may produce a better training hypothesis but cannot label an unsupported factual correction as established. It records the candidate, seeks more evidence within budget, and C2 keeps abstaining or reporting ambiguity. No human approval of every unresolved case is required; new source evidence can reopen the job. In the mechanics example, a question with no mass is never repaired by inventing a training label for the mass.

Learning closure

An episode is resolved only when an accepted release addresses the failure and its regression case passes. Other terminal statuses: unsupported by current scope, awaiting evidence, duplicate, rejected correction, budget exhausted. The journal links each cluster to the skills, datasets, model versions and deployment changes it caused (Releases and journal).

Worked example

Vision §12: C3 sees repeated confusion between "total force" and "net force", inspects usage and accepted definitions, writes a dossier, generates individual-versus-resultant contrast cases, adds validated labels, retrains with replay and evaluates on protected examples. If it passes, a new snapshot is published and the journal records episodes, evidence, dataset delta and metrics. If the patch later breaks multi-body questions, a monitor can trigger rollback to the compatible snapshot; the earlier dataset and adapter remain.

Episodes

C3 may use only episodes whose retention policy permits training; a no-retention session never becomes a hidden training source. The C2 episode record is described in C2 operation. The implemented dialog returns a trace that is the precursor of this record.

Failure modes

  • Unstable or expensive C3: narrow repair jobs, stronger replay, evidence thresholds, lower frequency (vision §17).
  • Patch that memorizes an episode: caught by new counterexamples in C3.05.
  • Concurrent job on an old parent snapshot: must rebase and repeat affected checks.
