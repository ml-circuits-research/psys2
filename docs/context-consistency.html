Context and consistency

Status: specified planned (vision only) Open world, conflicting answers and closed=true are in the interpreter; bridges, retraction and truth maintenance are planned (vision only).

Specs: spec 04 Interpreter, spec 02 Legends and worlds

Vision: vision §4

Purpose

A fact is meaningful within a context. This page covers the semantic rules that stop PSys2 from treating a pile of facts as one flat truth: contexts, identity, open versus closed world, assertion states and truth maintenance (vision §4).

Contexts

A context includes its document or session, world release, applicable version or effective interval, assumptions and interpretation branch. Inference checks context compatibility at every join. Importing a world makes its knowledge available for consideration, not applicable to every question. On a wire, the context is core.in. The rule formalizer stamps core.in=$<worldId> on every emitted wire (spec 03).

Identity bridges: core.same

core.same is an entity identity assertion with its own evidence, scope and confidence. It is not a command to merge all facts. A bridge declares which identifiers correspond and which attributes may be queried across it under which conditions. Two records for valve V2 can be the same device with different limits from two specification revisions; the question's effective date or chosen revision decides applicability, and if it does not, the result reports ambiguity.

@s1 core.same
    a=$spec2019.v2
    b=$spec2023.v2
    core.source="plant-notes.txt#40-88"
    core.in=$doc.plant-notes

Open and closed world

Open world is the default. Closed-world reasoning is allowed only for an explicitly bounded predicate, dataset snapshot and context with a completeness declaration. A world-level preference may select defaults but cannot turn an incomplete extraction into proof of absence: "no matching item found" and "the item does not exist" are different claims.

Vision and specs differ

The specs implement closed world as closed=true on a type in the legend. A question with mode=exists then returns no; otherwise unknown with status missing (spec 04). The vision additionally demands a snapshot and completeness declaration scoped to a context; that is narrower in the vision than in the spec.

Four assertion states

StateMeaning
supportedPositive assertion with accepted support
refutedExplicit negative assertion with accepted support
unresolvedNo sufficient support either way
conflictingBoth, or contradictory supported alternatives

Positive and negative assertions are stored independently. The core does not derive arbitrary conclusions from a contradiction. Each operation declares how it handles these states; ordinary deterministic calculations require compatible, unconflicted inputs. Specialized exception semantics belong to a declared backend (for example ASP, see Interpreter).

Scoped assertions

Conditional, hypothetical, quoted and reported assertions carry explicit scopes. "If pressure exceeds 5 bar, close V2" stores a condition and a guarded action, not a measurement. "The supplier claims X" stores an attributed claim unless world policy and evidence authorize treating X as established. Negation scope, quantification and temporal ordering use the discourse and time legends. The rule formalizer in v1 has no such scope patterns beyond what a world declares; scope handling is a main target of the encoder (Encoder formalizer).

Knowledge store and truth maintenance

  • The store distinguishes assertions, derivations, candidates and retractions. Source provenance and acceptance status are separate: a source can support a claim without establishing it.
  • Candidates that fail validation stay in quarantine with diagnostics, outside the active fact index.
  • Contradictory source material stays as separately scoped claims; it is never deleted to make a consistency test pass.
  • Truth maintenance records support sets, not a flat ancestor list (core.from may be repeated and may carry alternative supports). Retracting one support removes a conclusion only if no accepted alternative remains.
  • Default conclusions depend on the absence checks and completeness snapshots that licensed them; a new exception invalidates them. Identity bridges, imported versions and operation versions are dependencies too.
  • These rules are exercised by insertion, deletion and rollback tests before cross-world publication is enabled.

What exists now

The implemented interpreter distinguishes supported, conflicting and missing answers, honours closed=true, and records core.from for answers. Contexts beyond the session overlay and the world id, core.same bridges, retraction and support-set truth maintenance are specified only in the vision.

Failure modes

  • Joining facts across incompatible contexts: must be blocked by the compatibility check and reported as ambiguity.
  • Treating a missing extraction as proof of absence: forbidden unless a completeness declaration exists.
  • Deleting a contradictory source to pass a test: forbidden.
