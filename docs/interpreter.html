Interpreter

Status: implemented planned (vision only) JavaScript strategy, questions, requests, rendering implemented; Lean, Datalog, SMT, ASP, Prolog and assurance fields are vision only.

Specs: spec 04 Interpreter

Vision: vision §7, vision §8, vision §14

Purpose

The main interpreter answers questions and executes requests over a session overlay on top of the world knowledge bases. The current implementation (src/interpreter/, browser-safe) is the JavaScript execution strategy of vision §8 restricted to what the first worlds need. Lean and solver backends plug in later behind the same envelope.

Working memory

A session overlay: the session's wires (entities, facts and events, questions, answers) on top of the knowledge bases of the loaded worlds. Indexes: by id, by type (including ancestor types from legends), by (type, fullKey, value).

Questions

@w5 core.question
    type=kids.arith.holding
    seek=count
    where.owner=$e.tom
    where.item=apple
  • type: the wire type asked about. seek: a key of that type (short or full). where.<key>=v (repeatable): constraints. about=$id: ask about one wire. mode: value (default), exists (yes/no), list, count.

Resolution order

  1. If the sought key is compute=true and an operation lists it in outputs, run the operation(s).
  2. Otherwise direct lookup: wires of type (or a descendant) matching all where constraints with the sought key. One distinct value: supported. Several: conflicting with alternatives. None: next step.
  3. Operations whose outputs include the key.
  4. Nothing applies: missing, with the sought key and its legend ask text.

mode=exists returns yes (supported); no only if the type is declared closed=true in the legend, otherwise unknown (missing). Open world is the default.

Every answer is written to the session:

@a3 core.answer
    to=$w5
    value=8
    core.status=supported
    core.via=$op.kids.arith.currentCount
    core.from=$w1
    core.from=$w2

Requests

core.request action=<operation id or action name> arg.<name>=<value>... runs the operation with semantics=action whose id or action= matches. Actions change session state only (task lists, reminders, a game score). External effects need explicit capabilities (vision §8) and are out of scope for fixture worlds.

@w9 core.request
    action=add_task
    arg.text="buy pencils"

Operation declarations

@op.kids.arith.currentCount core.operation
    outputs=kids.arith.holding.count
    inputs=kids.arith.holding.owner
    inputs=kids.arith.holding.item
    impl=currentCount
    semantics=query
    doc="The number someone has after applying, in order, every giving, getting, eating and buying event."

semantics: query (reads), compute (pure function of inputs) or action (changes session state; action=<name> names it). impl names an export of the world's ops.mjs. The planner indexes operations by declared outputs and never guesses capabilities from function names (vision §3).

Vision and specs differ

Vision §3 operation declarations carry identity and implementation hash, preconditions, completeness declarations, execution backend, budget and cancellation, evidence (test suite, checker, theorem) and a failure contract. Spec 04 declarations have only outputs, inputs, impl, semantics, doc. Vision §14 also defines describe(), compile(snapshot) and run(artifact, query, context, budget) for strategies; spec 04 has plain function exports.

Operation implementations (ops.mjs)

export function currentCount(ctx, args) {
  // args: { owner: 'e.tom', item: 'apple', question: <wire> }
  return { status: 'supported', value: 8, from: ['w1', 'w2'], assumptions: [] };
}

Vision and specs differ

Vision §4 names four assertion states (supported, refuted, unresolved, conflicting), vision §1 lists the distinct C2 outcomes, and vision §14 adds assurance records, completeness and resource usage to the envelope. Spec 04 uses its own seven statuses (no refuted or unresolved; missing covers absence) and has no assurance field.

Budgets: recursion depth 8, 10,000 wires visited per question, 200 ms per operation call in the server (best effort in the browser). Exhaustion yields budget.

Rendering

@tpl.arith.count core.template
    for=kids.arith.holding.count
    text="{owner} has {value} {item:plural}."
@tpl.arith.count.missing core.template
    for=kids.arith.holding.count
    status=missing
    text="I don't know how many {item:plural} {owner} has."
@tpl.arith.ack.holding core.template
    for=ack.kids.arith.holding
    text="OK, {owner} has {count} {item:plural}."
  • for is a sought full key, an operation id, action.<name>, or ack.<type>. status defaults to supported.
  • Placeholders: {value}, any where/argument/wire key in short form, {x.name} drills into a referenced wire; entity references render as names.
  • Filters: :plural :singular :cap :a :list :number.
  • Fallbacks: supported gives the value (with unit); missing gives I don't know yet. <ask of the key>; conflicting gives I have conflicting information: <alternatives>.; unsupported gives I can't do that yet.; statement acknowledgement gives OK.
  • The renderer never adds facts absent from the envelope (vision §7).

Execution strategies and assurance (vision §8)

planned (vision only) Everything in this section except the JavaScript strategy.

The main interpreter performs indexed lookup, context-aware unification, bounded planning, memoization and provenance assembly over finite typed relations and declared pure operations. Recursive rules must declare their fragment; "equivalent to Datalog" is claimed only for the explicitly supported Datalog fragment. Each backend implements the same result contract and is not assumed to share semantics with the others.

Assurance fields

FieldMeaning and required evidence
ExecutedA named implementation produced the result from recorded inputs
Independently checkedA separate checker verified the result or a certificate for the stated property
Proof checkedA proof artifact for a specific proposition accepted under the recorded Lean environment and axiom policy
Interpretation evidenceExtraction, scope, identity and calibration information linking text to premises

Assurance is recorded by property, never as one universal "verified" badge. A unit theorem does not prove the numerical answer, the source interpretation or real-world applicability. Tests between JavaScript and Lean do not transfer a Lean theorem to JavaScript execution.

Effectful actions

Effectful operations declare target capabilities, preconditions, expected effects, idempotency keys, dry-run support and recovery. The reasoning engine creates an action plan; an action gateway executes only capabilities authorized for the session; observations after execution become episode evidence. Rolling back a world version does not undo an email or device command; such actions need their own compensation operations, which may be unavailable. Not in the specs beyond session-state actions.
