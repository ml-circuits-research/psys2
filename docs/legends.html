Legends

Status: implemented

Specs: spec 02 Legends and worlds, spec 01 SOP Lang v1

Vision: vision §3, vision §2

Purpose

A legend is a versioned vocabulary of wire types and keys. Each key declares its natural-language question, value type, cardinality, and whether it can be observed, computed or both. Questions guide encoder training and query mapping; they are not inference rules by themselves (vision §3). A legend is itself SOP Lang.

Format

@legend.kids.arith core.legend
    namespace=kids.arith
    version=0.1.0
    imports=core
    imports=kids.common
    doc="Counting and simple arithmetic about things people have"

@kids.arith.holding core.type
    extends=core.state
    doc="Someone has a number of items of one kind"
    example="Tom has 5 apples."

@kids.arith.holding.owner core.key
    value=$kids.common.agent
    card=one
    ask="Who has them?"

@kids.arith.holding.count core.key
    value=integer
    card=one
    ask="How many are there?"
    observe=true
    compute=true
Wire typeEntries
core.legendnamespace (required), version (semver), imports (repeatable namespaces), doc
core.typeid is the full type name; extends (default core.thing), doc, example (repeatable), negative (repeatable example that is not this type); closed=true declares a predicate closed-world (spec 04)
core.keyid is <type>.<key>; value is a literal kind (integer, number, string, atom, boolean, quantity.<kind>, time.<kind>) or a type reference ($kids.common.agent); card = one (default) or many; ask (required English question); observe / compute (default observe=true compute=false); required (default false)

The bootstrap legends core (worlds/core/legend.sop) and quantity live in worlds/ like any other namespace.

Key resolution, step by step

  1. Take the wire type T and the written key k.
  2. If k contains a dot and resolves as a full key, use it. core.* keys are always available in full form.
  3. Otherwise try T.k, then A.k for each ancestor A of T, nearest first.
  4. Exactly one resolution is required. Ambiguity or failure is a validation error.
@w1 kids.arith.holding owner=$e.tom count=5 item=apple
# "count" resolves to kids.arith.holding.count
# the legend, not the parser, decides this

Validation of a wire against legends

  • the type is known;
  • every key resolves;
  • cardinality is respected (card=one forbids repetition);
  • literal kinds parse (integer, number, boolean);
  • references point to a wire whose type is the declared type or a descendant (checked when the target is available).

The vision adds that fully qualified keys are canonical and that legend imports resolve through a lockfile to exact release hashes (§2, §3). Type extension is allowed only if parent invariants and operation preconditions stay valid, and a changed meaning gets a new identifier or a declared migration.

Vision and specs differ

The vision wants a normalization rule per key and context rules and entity bridges in the legend (C1.02). Spec 02 keys have no normalization entry, and lockfile pinning is not specified; imports are plain namespace names.

Namespaces

A legend owns one namespace, the world directory is named by it (worlds/kids.arith/), and ids differ by prefix: @legend.kids.arith for the legend and @world.kids.arith for the world (vision §2). Namespace reuse is measured for usefulness, not rewarded by a percentage target (vision §3).
