Releases and journal

Status: planned (vision only)

Specs: none (vision only)

Vision: vision §11, vision §15

Purpose

This is how changes become part of the live assistant and how they are undone. The central engineering rule: a proposed change is built in a candidate snapshot, evaluated by a separate gate and published atomically; failed candidates remain inspectable; the active assistant keeps using an accepted snapshot until a replacement passes (vision §11, §15). Not implemented: the current repo has fixture worlds and a version field, but no registry, journal, snapshots, gate or rollback.

Release and rollback flow

Versions and snapshots

A world release is an immutable manifest of artifact hashes: legend, imports, context policy, sources, knowledge snapshot, operations, implementations, adapters and heads, backbone and tokenizer, training data, evaluation record, calibration, rendering templates. A deployment snapshot pins a compatible collection of world releases, router release, runtime versions and global policies. Version numbers are labels; hashes are identity.

Lifecycle and promotion

States: draft, building, evaluated, rejected or accepted, then shadow, active, superseded or quarantined. Passing evaluation does not change the active pointer. Promotion is a compare-and-swap against the expected parent snapshot; concurrent jobs based on an old parent must rebase and repeat affected checks. Writes to candidate workspaces never mutate accepted releases.

Gates

The release service owns protected tests and policy thresholds. A candidate must fix its motivating regression, satisfy critical invariants, meet its declared coverage contract and stay within regression tolerances (at most 2 percentage points loss in unchanged noncritical metrics). Changes to tests, thresholds or coverage are logged and evaluated separately. The agent cannot repeatedly inspect a hidden set and keep calling it unseen. See Evaluation.

The journal

Field groupRecorded content
Identity and timeEvent id, parent event hash, timestamp, job, skill, actor
MotivationRequest or episode cluster, observed failure, source change, intended improvement
Evidence and changesSources, examples, claims added or retracted, code and schema diff, migrations
LearningData hashes and split lineage, model and recipe, GPU run and costs
EvaluationOld and new metrics, test manifests, limitations, gate decision, policy version
DeploymentPrevious and new snapshots, promotion or rollback reason, affected worlds

Entries are append-only and tamper-evident through hash linking (this does not stop an administrator deleting storage; durability needs backups and retention). Failed attempts are first-class records. The journal can answer what was learned, when, from which evidence, why, what was tested and which deployment used it. Illustrative shape in SOP Lang (not defined by any spec):

@j42 core.journal
    parent=$j41
    kind=rollback
    from="snap-9c1"
    to="snap-4b7"
    reason="invariant failure in multi-body questions"
    core.in=$deploy.main

Rollback

  1. Switch the active deployment pointer to an available compatible snapshot (policy-authorized, atomic).
  2. Requests in flight finish on their pinned snapshot or are cancelled; a request never changes versions midway.
  3. Sessions stay pinned or migrate through a tested conversion that marks invalidated assertions.
  4. Record a new journal event and start a diagnosis job. The failed release and its evaluation record are not deleted.

Rollback does not undo external effects (see Interpreter, effectful actions).

Retraction, retention and replay

  • Source retraction triggers dependency analysis: derived assertions lose invalid supports; adapters trained on retracted examples are marked affected and scheduled for clean retraining. Removing a fact from the KB does not erase its influence on model weights; until retraining passes, policy may quarantine the capability, state a limitation or use an unaffected release.
  • All supported snapshots retain rollback artifacts. Garbage collection follows reachability from active, rollback and audit roots; a backup-and-restore test verifies it. Retention expiry can make replay or rollback unavailable and must be visible.
  • Deterministic interpreter replay is required for a pinned environment and inputs; bitwise equality of GPU inference or training across hardware is not promised.

Failure modes

  • Crash during fine-tuning, indexing or promotion: the previous accepted snapshot stays intact.
  • Lost connection with unknown completion state: the job journal distinguishes it from a failed computation; recovery inspects committed artifacts first.
  • Stale parent at promotion: compare-and-swap fails; rebase.
