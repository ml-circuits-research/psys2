Purpose

How PSys2 is split into processes, which code is trusted and how resources are managed (vision §13). Status: the Node orchestration core and the HTTP server exist in the fixture implementation; sandboxing, GPU workers, schedulers and inference workers are vision only.

Process layout

PartImplementationNotes
Orchestration core: parsing, registries, scheduling, HTTP, graph operationsNode.js .mjs, standard library onlyThe "no external dependencies" rule applies to the core package, not the whole system
Model training and inferenceSeparate managed processes, pinned Python and ML dependencies (training/)Never imported by the Node core
Lean and solver backendsExternal workersOptional, same result contract
Owner servicesLearning service (scheduler, source registry, candidate workspaces, GPU queue); operation service (sessions, accepted snapshots); release service (promotion, rollback)Distinct access rights; the coding agent cannot move the production pointer

Isolation of generated code

  • Generated interpreters are untrusted code before and after testing. They run inside an operating-system isolation boundary: explicit filesystem mounts, network denied by default, unprivileged identity, process and memory limits, enforced timeouts. The sandbox is tested against forbidden file, network and process access.
  • node:vm and worker_threads are not sufficient security boundaries (vision reference [2]); worker threads remain fine for trusted internal parallelism.
  • Coding-agent workspaces reach only permitted sources and tools; evidence-acquisition network access is scoped by learning policy. LLM calls come from the agent service, never from generated interpreter code or C2. The agent cannot obtain release credentials or protected answers. Uploaded documents are data, even if they try to instruct the agent.

Vision and specs differ

The fixture worlds' ops.mjs is hand-written, trusted, browser-safe JavaScript that is imported directly into the process (spec 02, 04). The sandbox rules apply to generated operations from C1 and are not enforced in the current implementation. The server only enforces best-effort per-call time budgets (200 ms).

Resources

  • Hardware discovery records GPU memory, CPU, RAM, storage and precision support; a smoke benchmark sets usable batch and sequence limits before jobs are admitted. Training, inference, compilation and solver queues are separate and expose utilization and contention. A CPU profile is evaluated for inference; GPU training is not forced onto CPU.
  • Inference workers expose a versioned local protocol: batching, adapter load/unload, prediction with scores and offsets, cancellation, health checks. Responses name the exact model artifacts. Adapter caches are bounded and eviction cannot substitute a newer release under the same label.
  • Storage sizing counts models, datasets, sources, checkpoints, indexes, journal and retained releases; a small adapter does not mean a small world. Shared immutable artifacts are deduplicated. Estimates come from pilot builds; no fixed GPU-day count is assumed.

Crash safety

Job steps write to temporary locations, verify hashes and commit manifests atomically; retries use idempotency keys; a crash during fine-tuning, indexing or promotion leaves the previous snapshot intact (Releases and journal).

Failure modes

  • GPU out of memory: reduce batch or sequence budget per declared policy, recorded.
  • Sandbox escape attempt: denied by the OS boundary; must be covered by fault-injection tests.
  • Adapter loaded against a different backbone or tokenizer: forbidden.
