SOP Lang v1

Status: implemented

Specs: spec 01 SOP Lang v1

Vision: vision §2

Purpose

SOP Lang is the minimal graph serialization in which everything PSys2 knows, asks and answers is written. A wire has an identity, a type and key-value entries. A circuit is a set of wires connected by references. The syntax knows nothing about any domain: legends (see Legends) and operations (see Interpreter) give the values meaning.

Wire syntax

@wireId wireType key=value key=value ...

Example from the vision (a mechanics circuit; keys are written in short form and resolved by the pinned legend):

@b1 phys.mech.body mass=2kg
@f1 phys.mech.netForce on=$b1 magnitude=10N
@a1 phys.mech.acceleration of=$b1
@q1 core.question about=$a1 seek=phys.mech.acceleration.magnitude
  • A declaration starts with an unquoted @ and ends right before the next unquoted @ or at end of input. It may span any number of lines.
  • wireId and wireType are identifiers: one or more segments [A-Za-z_][A-Za-z0-9_-]* joined by . (b1, kids.arith.holding, legend.kids.arith).
  • An entry is key=value with no spaces around =. Keys are identifiers.
  • Tokens are separated by whitespace (spaces, tabs, newlines).
  • Comments (v1.1): # where a token could start runs to the end of the line; variables ?name are a fourth value kind, legal only in wires a rule names (spec 01). A doc="..." entry or a core.note wire still carries a note that must be kept.
  • A repeated key is kept as several entries in order. Whether repetition is legal is decided by the legend (cardinality), not by the parser.

Values

KindFormExamples
string"..." with JSON string escapes. @, $, = inside strings are ordinary text."Tom has 5 apples.", "a \"quoted\" word"
reference$ followed by an identifier$b1, $legend.kids.arith
atomany non-empty token without whitespace, ", @, $, = or \2kg, 10N, true, 3.5, -4, kids.arith.holding.count

Atoms such as 2kg stay opaque to the parser. Parsing quantities into exact values, dimension checks and unit conversion belong to the quantity module (vision §2, bootstrap legend quantity), and decimal input uses decimal or rational semantics where an operation requires exactness.

How parsing works, step by step

  1. Scan the text. Whitespace is skipped; the first non-whitespace character must be @.
  2. Read the wire id and type as identifiers.
  3. Read entries until the next unquoted @: key, =, then a string, a reference or an atom.
  4. Record the wire with its span (start, end, line) and source.
  5. Collect every error with offset, line and column rather than stopping at the first; check duplicate wire ids at the end of the parse unit.

Errors: no silent repair

The parser rejects, with a character offset, line and column:

  • text before the first @ other than whitespace;
  • a declaration without id or type;
  • a token that is not key=value after the type;
  • an empty value (key=), an unterminated string, a bad escape;
  • an invalid identifier in id, type, key or reference;
  • a duplicate wire id within one parse unit.
@w1 kids.arith.holding owner=$e.tom count=
@w2 kids.arith.holding note="unterminated

Parser API

Implemented in src/soplang/index.mjs (browser-safe: no node:* imports).

parse(text, { source }) -> { wires: Wire[], errors: ParseError[] }
// Wire = { id, type, entries: [{ key, value }], span: { start, end, line }, source }
// value = { kind: 'atom', v: '2kg' } | { kind: 'string', v: 'free text' } | { kind: 'ref', v: 'b1' }
// ParseError = { message, offset, line, column, source }
parseOrThrow(text, opts) -> Wire[]          // throws SopSyntaxError listing all errors
serialize(wires, { canonical }) -> string   // one wire per block, entries one per line, 4-space indent
get(wire, key) -> value | undefined         // first value
getAll(wire, key) -> value[]

Canonical form

Canonical serialization exists for hashing and stable diffs:

  • wires stay in input order;
  • entries are sorted by key, keeping the relative order of repeated keys;
  • strings are re-escaped with JSON escapes; atoms and references are unchanged;
  • \n line endings and a trailing newline.
@a3 core.answer
    core.from=$w1
    core.from=$w2
    core.status=supported
    core.via=$op.kids.arith.currentCount
    to=$w5
    value=8

Vision and specs differ

The vision (§2) also requires set-valued keys to be sorted canonically, ordered collections to use explicit list nodes, and cross-artifact references to be typed core.ref records (world id, release hash, wire id). Spec 01 defines only entry sorting by key; core.ref and list nodes are not in the specs yet.

Short and full keys

Keys may be written short (mass) inside a wire of type phys.mech.body. The legend layer resolves them to full keys (phys.mech.body.mass) against the type and its ancestors. A key containing a dot is treated as full when it resolves, otherwise as short. Resolution is unambiguous or an error. The parser itself never resolves keys; see Legends.

Core keys (namespace core)

KeyMeaning
core.sourceSource record reference or locator ("kids-story.txt#12-48"), with exact span when known
core.inContext (world, session, document, assumption branch)
core.fromSupporting wires (repeatable)
core.viaOperation or pattern id and version that produced the wire
core.statusasserted, derived, candidate, retracted, supported, refuted, unresolved, conflicting

The rule formalizer additionally stamps core.seq (strictly increasing per session) on emitted wires; see Rule formalizer.

Vision and specs differ

Vision §2 defines core.source as a reference to an immutable source record including content hash and exact span; core.in as a context with world snapshot, scope, assumptions and time; core.via with an exact implementation version; and says core.status is never inferred from a confidence number. The spec uses simpler locators and ids for the current implementation, and its core.status list merges lifecycle states (asserted, derived, candidate, retracted) with the four observable states of vision §4. Answer envelopes in spec 04 use a different status set again (see Interpreter).

Failure modes

  • Syntax error: reported with position, nothing repaired; the dialog layer never sees a half-parsed wire.
  • Duplicate wire id inside one parse unit: rejected.
  • Illegal repetition of a key or unknown key: not a parser error; reported by legend validation.
