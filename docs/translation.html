Translation

Status: specified (draft) implemented Spec is a draft; the Romanian-English rule translator is part of the current implementation.

Specs: spec 05 Translation, spec 06 Dialog, server, webchat

Vision: vision §5

Purpose

Everything PSys2 stores is English (AGENTS.md). Input in another language is translated to English at the system boundary before formalization; answers can be translated back. The goal is meaning preservation for formalization, not literary quality: English that the rule patterns (and later the encoder) read correctly, with every meaning-bearing element kept and traceable to the source. Nothing stored in a world, KB, episode or journal is in another language; the original text is kept only as a source record referenced by core.source.

Vision and specs differ

Spec 05 is a draft for discussion. The vision does not define boundary translation; vision §5 instead says each additional language requires an explicit encoder profile, data and evaluation rather than an assumed multilingual capability. Spec 05 lists this tension as an open question.

Interface (src/translate/, browser-safe)

detectLanguage(text) -> { lang: 'en' | 'ro' | 'unknown', confidence }
translate(text, { from: 'ro', to: 'en' }) -> {
  text,                     // English text
  alignment: [{ src: [s, e], tgt: [s, e] }],   // spans, so core.source can point into the original
  unknown: [{ word, span }],                    // source words the translator could not map
  notes: [string],                              // e.g. "gender of 'el' kept as 'he'"
  confidence                                    // share of source content words that were mapped
}

First language pair: Romanian and English.

Contract

  • Proper names, numbers and units pass through unchanged and are always aligned.
  • Unknown content words are not dropped: they pass through and are listed in unknown, so the dialog can say which word it did not understand.
  • Negation, quantifiers, conditionals (dacă to if), question words and tense of events are always translated; a sentence whose negation or question word cannot be mapped is reported untranslatable rather than translated without it.

Approach (rules, no model), step by step

  1. Normalization: Unicode NFC; both comma-below and cedilla forms of ș/ț; diacritic-less input (cate mere are Ion) accepted through diacritic-insensitive lexicon lookup.
  2. Morphology: strip Romanian definite articles and case endings to a lemma (mărul, merele, merelor to măr), detect plural, map verb forms to lemma, person and tense for lexicon verbs (are, au, avea, dă, a dat, primește, mănâncă, cumpără).
  3. Phrase table first: multi-word expressions and question frames.
  4. Word-by-word fallback with the bilingual lexicon (src/translate/lexicon.ro-en.mjs) and English re-inflection (plural after numbers above 1, third-person -s, does ... have frames).
  5. Back translation (en to ro) uses the lexicon in reverse plus per-world answer templates.

câte ... are Xhow many ... does X have

Example round trip (illustrative): Câte mere are Ion? becomes How many apples does Ion have?, formalized by the rule strategy, and the answer is rendered back in Romanian.

Evaluation (proposed)

Round-trip formalization equality: the Romanian test must produce the same wires as its English twin. World tests can set language=ro to exercise this (Worlds).

Failure modes

  • Unknown word: passed through, reported in unknown.
  • Unmappable negation or question word: untranslatable, reported.
  • Low confidence: surfaced to the dialog layer.
