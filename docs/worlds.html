Worlds

Status: implemented World directory, manifest, lexicon and tests are implemented as fixtures; data manifests, adapters and release hashes are vision only.

Specs: spec 02 Legends and worlds, ADR-001

Vision: vision §3, vision §6

Purpose

A world is a versioned computational package: legends and imports, sources, knowledge, operation declarations and implementations, templates, tests and, in the full vision, model artifacts, training data, evaluation data, calibration, policies and history (vision §3). Document worlds hold document-local terms and assertions while importing reusable domain operations. A world may have an empty knowledge base but must still have a data manifest and an explicit learning status.

World directory

One directory per world under worlds/, named by namespace.

FileContents
world.sopOne core.world wire (manifest)
legend.sopThe world's legend (Legends)
lexicon.sopWord lists used by the rule formalizer and router (core.lexicon wires)
patterns.sopRule-formalizer patterns (core.pattern wires), see Rule formalizer
operations.sopOperation declarations (core.operation wires), see Interpreter
ops.mjsJavaScript implementations (browser-safe, no imports except relative ones inside the world)
kb.sopKnowledge base: asserted facts, each with core.source
templates.sopAnswer rendering templates (core.template wires)
tests.sopCompetency tests (core.test wires)

Manifest

@world.kids.arith core.world
    namespace=kids.arith
    version=0.1.0
    legend=$legend.kids.arith
    imports=world.core
    imports=world.kids.common
    formalization=rules
    language=en
    status=fixture
    title="Counting and arithmetic (primary school)"
    doc="Who has how many things; giving, getting, buying; adding and taking away."
  • imports lists world ids. Importing makes the legend, lexicon, patterns, operations, templates and knowledge available for consideration, not automatically applicable (vision §4; see Context and consistency).
  • formalization: rules (Rule formalizer) or encoder (Encoder formalizer; not implemented yet). ADR-001 says a world may later declare both, with the encoder preferred where accepted.
  • status: fixture, candidate, accepted.

Fixture versus accepted

StatusMeaning
fixtureHand-built platform fixture or demo, made before C1 is automated so parser, interpreter, dialog, router and webchat can be tested end to end. Not produced by the C1 workflow, must say so, does not count toward C1 acceptance targets and is never presented as autonomously learned (ADR-001, AGENTS.md).
candidateBuilt but not passed through the release gate.
acceptedPassed the independent gate (Releases and journal). In the vision this means protected tests, operation checks, regression and a coverage manifest.

Lexicon

@lex.kids.arith.items core.lexicon
    class=noun
    word=apple word=pear word=sweet word=marble word=pencil
@lex.kids.arith.triggers core.lexicon
    class=trigger
    word=how_many word=more word=left word=altogether word=gives

class is noun, name, verb, unit, trigger or world-defined. Multi-word entries use _. Plurals are derived by the rule engine; irregular ones are declared as plural=child:children.

Shared phrasing: macros, lang.common, shapes

A world does not repeat common phrasing. lexicon.sop may hold core.phrase wires (phrase.<id>, alt= lines, frame=false for content words) that patterns use as [$id] macros; lexicons may use extends= and exclude=. The shared fixture world lang.common (no patterns, imported by kids.common, so every world sees it) holds lead-in, suffix, filler, yes/no and shape phrase groups and the shared lexicons; the same lists back ctx.lang in operation code. patterns.sop may hold core.shape wires (family, verb, obj, val, noun, det, link, mod, objmod, extra, emit, emitOpts, forms, skip, priority, kind, sample, example, pron, rel, objdet, cont, poss), expanded at load into the request-form patterns; node scripts/expand-patterns.mjs <world> shows them. Rule: new phrasing goes into lang.common or a shape, never inline. See Rule formalizer for the details, canonical= example marks (RD6) and the routing keys tabOnly, tabFollow, tabPriority, yieldsTo, needsState.

Tests

@t.arith.1 core.test
    input="Tom has 5 apples. Ana gives him 3 apples. How many apples does Tom have?"
    expect="8"
@t.arith.2 core.test
    input="How many apples does Mia have?"
    expectStatus=missing

expect is a substring of the rendered answer to the last question in input; expectStatus is the answer status (Interpreter). language=ro exercises translation; session= groups tests that share one dialog session, run in id order. Run with node src/cli.mjs test-world <id|all>; every world must pass.

Data ownership (vision §3, §6)

Every accepted world owns its fine-tuning material: train and development splits, machine-readable labels, negative examples, source lineage, generation recipes, tokenizer and backbone identifiers, adapter configuration, trained heads, training logs and evaluation manifests. Shared datasets are referenced by immutable hash instead of copied. A world cannot be published as encoder-capable with only a model file and no reproducible data lineage. Model isolation uses a pinned common backbone with a separately trained adapter per world: inheritance of vocabulary and operations does not merge adapters, and a child adapter is trained on the same backbone with local data plus pinned, licensed parent replay data.

Imports resolve through a lockfile to exact release hashes; overrides are explicit, scoped and tested and do not rewrite imported history.

Vision and specs differ

Spec 02 has no data manifest, training data, adapters, lockfile or evaluation record; its status values (fixture, candidate, accepted) are not the vision lifecycle (draft, building, evaluated, rejected, accepted, shadow, active, superseded, quarantined; §11). Vision §3 requires a data manifest even for empty worlds; fixture worlds have none. This is accepted for fixtures under ADR-001. Also, spec tests are visible competency tests, not the protected acceptance sets of vision §6 and §15.

Failure modes

  • Missing world.sop or legend.sop: the world does not load.
  • Import of an unknown world: load error.
  • A status=fixture world that does not declare itself a fixture violates AGENTS.md.
  • Failing tests.sop: test-world fails and npm test must not pass.
