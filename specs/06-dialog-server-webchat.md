# 06 — C2 dialog pipeline, server API and the browser webchat

## Dialog pipeline (`src/dialog/`, browser-safe)
```js
const engine = await createEngine({ loader })   // loads all worlds via the loader
const session = engine.createSession({ language: 'auto' })
const reply = await session.send(text)
// reply = { text, parts, lang, translation, segments, wires, answers, statuses, trace }
```
Steps for every user message:
1. **Language**: detect; if not English, translate to English (spec 05). Keep the original as the source record.
2. **Formalize** with the rule formalizer over all loaded worlds (spec 03). Emitted wires go to session memory.
3. **Solve**: every `core.question` and `core.request` is resolved by the interpreter (spec 04).
4. **Render** each result with world templates; statements get acknowledgements; unparsed sentences get: `I did not understand "<sentence>".` plus up to two example sentences from the closest world (router score). The `capabilities` answer ("What can you do?") is one short sentence built from the `summary=` of every world manifest (spec 02).
5. **Back-translate** the reply if the user wrote in another language. The reply is built as **parts** `[{ text, translate, quote?, example? }]`: `translate: true` parts are back-translated (consecutive ones together), `translate: false` parts are kept verbatim. Text quoting the user (`I did not understand "<sentence>"`, the unknown words) is a `translate: false`, `quote: true` part holding the user's ORIGINAL sentence (found through the translation alignment), never the English translation. Each example sentence is translated separately by the translator and quoted as a `translate: false`, `quote: true`, `example: true` part; an example whose translation reports unknown words is omitted, and the whole lead-in is omitted when none is left. `reply.parts` exposes the final parts (already in the reply language; `reply.text` is their concatenation) so the webchat can style quotes. The dialogue layer's own sentences (undo, "why?" / "what did you do?", bare yes or no, refusals) are built the same way: English text as `translate: true` parts, the user's own words as `translate: false`, `quote: true` parts taken from the turn's source record (`original`), and the answer shown earlier (already in the reply language) as a `translate: false` part. Nothing is written to the user outside the parts. `tests/ro-matrix.test.mjs` (with `training/eval/ro-matrix-sessions.json`) runs a Romanian session in both reasoners, fails on any reply that stays English and checks that every sentence reached the translator.
6. Return the reply and a `trace` (segments, router scores, matched patterns, wires, operations called, statuses), which is the episode record (vision §7).

`engine.worlds()` lists loaded worlds; `session.memory()` returns the session wires as SOP Lang.

Tool-world additions (spec 07): `reply` also has `state` (snapshot of each world state that changed during the message, by world id), `effects` (`[{ name, args, world }]` in order) and `trace.intercepted` / `trace.effects` / `trace.formalizer` / `trace.routing` (one routing decision per segment: tier, reason, winner, runner-up, context; tier 1 for a modal intercept; spec 03 section 4, ADR-004). `session.context()` returns the routing context (active tab and its owner world, active game world, modal world, recent and last worlds); the host sets the active tab with `setWorldState('ui.shell', { activeTab })` and an active game with `{ activeGame: '<world id>' }`. `session.state(worldId?)` returns the current state; `session.setWorldState(worldId, patch)` is the host's way to change state (a click on a tab): shallow merge, no reply, no effects; `session.observe({ effect, ok, detail })` records a `core.observation` wire. Correction phase (spec 03 section 1c, review G2): `send` first resolves self-corrections ("knight to f3, no, knight to c3") on the whole English message, ahead of the modal interceptors, discourse and formalization; the result is `trace.selfCorrections`. Modal input: before formalization the engine offers the (translated) text to `interceptInput(ctx, text)` of every world whose state has a truthy `inputMode`; the first `{ handled: true, reply? }` consumes the message. `engine.formalizers` is `{ rules, encoder }`; `session.formalizer` (writable), `createSession({ formalizer })` and `send(text, { formalizer })` choose the preference.

## Loaders
- Node: `src/loaders/fs-loader.mjs` reads `worlds/*/` and imports `ops.mjs` with dynamic `import()`.
- Browser: `src/loaders/bundle-loader.mjs` reads a bundle produced by `scripts/build-webchat.mjs` (`worlds/index.json` with file texts) and imports each world's `ops.mjs` from its copied path.

## Server (`src/server/`, Node only)
`node src/server/index.mjs [--port 8080]` — `node:http`, no framework. JSON in and out.
| Method and path | Behaviour |
| --- | --- |
| `GET /v1/health` | `{ ok, version, worlds }` |
| `GET /v1/worlds` | world manifests |
| `GET /v1/worlds/{id}` | manifest, legend summary, tests summary |
| `POST /v1/sessions` | `{ language?, formalizer? }` → `{ sessionId }` |
| `POST /v1/sessions/{id}/messages` | `{ text }` → reply object |
| `GET /v1/sessions/{id}/memory` | session wires as SOP Lang (`text/plain`) |
| `POST /v1/learn/*`, `POST /v1/worlds/{id}/improvements` | `501` with a pointer to the vision (C1/C3 not implemented) |

Sessions are kept in memory with an idle timeout (30 min). No LLM is reachable from this process.

## CLI (`src/cli.mjs`)
- `node src/cli.mjs chat` — interactive C2 dialog in the terminal.
- `node src/cli.mjs test-world <id|all> [--jobs N]` — runs the world's `tests.sop`. `all` runs the worlds in `min(N, worlds)` worker threads (default `os.availableParallelism()`, `--jobs 1` = in-process); lines are printed in world order and the exit code is the same as a serial run.
- Parallel evaluation tools (`scripts/lib/shard.mjs`): `scripts/eval-operational.mjs`, `eval-rules.mjs`, `eval-dispatch.mjs` and `npm test` (`scripts/run-tests.mjs`) take `--jobs N` (default all cores). `eval-operational --jobs 1` is the single-thread CPU latency measurement; with N > 1 each worker loads the engine and the ONNX session once (intraOpNumThreads 1), results are merged in the original order and totals are identical, but per-message latency (measured inside the worker) includes CPU contention. The output states the mode (`single-thread` or `sharded xN`).
- `node src/cli.mjs parse <file.sop>` — parse and report errors.
- `node src/cli.mjs formalize "<text>"` — print the emitted wires.

## Webchat (`docs/webchat/`)
A static page that runs C2 entirely in the browser, with no server: the same `src/` modules copied by `scripts/build-webchat.mjs` into `docs/webchat/lib/` and the worlds bundled into `docs/webchat/worlds/`. It shows the chat, and on demand the trace (wires, patterns, operations) so the demo makes the reasoning visible. It must work when opened from GitHub Pages (`/docs` folder) or any static server; ES modules require HTTP, so `file://` is not a supported way to open it.

### Webchat features (ADR-002)
- Language selector: interface, translation direction, speech recognition and speech synthesis language (English and Romanian at least): one language for all of them (see "The selected language is the only language" below).
- Translation: `browser-api` strategy when the browser offers an on-device translator (feature-detected), otherwise the `rules` translator; the trace shows which one was used and whether the checker fell back.
- **The selected language is the only language (LANG-FIXED, user decision).** `settings.language` (`en` | `ro`) is the single source of truth, owned by `docs/webchat/ui/language.mjs` (`get()`, `set(lang, reason)`, `onChange`, the BCP-47 tag `en-US`/`en-GB`/`ro-RO`). The selector (header or Settings > Language) and an explicit switch command ("vorbește în engleză", "switch to Romanian", "speak English": the `ui.shell` `ui.language` operation; the host moves the selector and the reply confirms, "Bine, am trecut la engleză.") are the only things that change it. Every message is read, answered, recognized and spoken in it: with Română selected every message goes through ro→en (English words such as "ok" or "stop" pass through the Romanian pipeline) and every reply comes back in Romanian, with no per-message detection, no `sessionLang`, no reply-driven switch (`switchedLanguage` is gone) and no `auto` mode in the webchat (the engine's `auto` remains for the CLI and the server only). A saved `auto` migrates once (settings version 3) to the browser language (`ro*` → ro, otherwise en) and is saved; the saved `speechLang` is dropped (an `en-GB` becomes `englishVariant`).
- **Language hint (the only use of the detectors).** Setting `languageDetection` (`auto` | `browser-api` | `rules`, labelled "Language hint"). After a TYPED message that is clearly in the other language (rules evidence strong, the detector agrees, at least 3 words and 8 letters) the page shows one note line, "Pare engleză — schimb limba?" / "That looks Romanian — switch the language?", with a button; the check is the engine worker's `hint` request, run after the reply, never on the turn path, never for voice, never switching by itself. The browser `LanguageDetector` is therefore called by nothing else (a spy test asserts no call in voice turns).
- Microphone button: dictation with the Web Speech recognition API in the selected language; the recognized text is sent as a message.
- Speaker toggle: when on, every answer is read aloud with the speech-synthesis API in the selected language.
- Missing browser APIs disable the corresponding control with a tooltip; nothing else depends on them.

## Formalizer strategies (one interface)
The rule formalizer (spec 03) and the encoder formalizer (vision §5, ModernBERT + per-world LoRA) implement one interface, so everything after formalization (interpreter, operations, tools, effects, rendering) is identical whichever formalizer produced the wires; only the quality of the SOP Lang differs.

```js
// src/formalizer/strategy.mjs
{ id: 'rules' | 'encoder', available(): boolean | Promise<boolean>, supports(world): boolean,
  formalize(text, { worlds, session, source }) -> same result shape as spec 03 }
```
- `createRulesFormalizer()` — always available; supports every world that has `patterns.sop`.
- `createEncoderFormalizer({ endpoint })` — talks to an inference worker (vision §13); until one exists it reports `available() === false`.
- `createDispatcherFormalizer({ load, getPolicy })` (`src/dialog/encoder-dispatch.mjs`) — the in-browser encoder strategy: a small dispatcher model (DistilBERT int8 ONNX) proposes segmentations and the top-3 worlds per piece, the rule validation layer (spec 03 §7) picks the reading, the rules of the chosen world produce the wires. It is installed as `engine.formalizers.encoder` by the host and attached with `attach(engine)`; the model is loaded lazily (`prepare()` or the first message), `onStatus(fn)` reports `idle | loading | ready | error`. When validation fails or the model cannot load, the segments come back unparsed / the strategy is unavailable and the rule formalizer is used. `reply.trace.dispatch` carries the candidates and why the winner won (spec 03 §7.7).
- Selection: the session setting `formalizer` (`'rules'` in the library; the webchat defaults to `'encoder'`) is a preference. For each world, the preferred strategy is used if it is available and `supports(world)`; otherwise the rule formalizer is used. The trace records, per segment, which strategy produced the wires.
- The webchat settings panel exposes the choice; the server accepts `{ formalizer }` when creating a session.

### Webchat model loading and leniency settings
- **Settings version** (`docs/webchat/ui/settings.mjs`, `SETTINGS_VERSION = 2`): defaults `formalizer: 'encoder'`, `spellcheck: true`, `partialUnderstanding: true`. A saved v1 record (no `settingsVersion`) with `formalizer: 'rules'` was the old default, not a choice, so it is migrated to `'encoder'` once and written back with the new version; any later explicit choice is saved with the current version and respected. Unknown values fall back to the default. Version 3: language is always `en` or `ro`. **Version 4 (2026-11-11):** `reasoner` defaults to `'matrix'` (spec 15); a saved `'ops'` of an older version is migrated once to `'matrix'` (it cannot be told from the old default), an `'ops'` chosen at version 4 or later is respected.
- **Model loading** (`docs/webchat/ui/dispatcher-host.mjs`): at page load `models/dispatcher/meta.json` is fetched with `cache: 'no-cache'`; the model files are kept in the Cache API (`psys2-dispatcher-model`) under keys carrying `meta.version.sha256`. Same sha256: loaded from the cache without a download. New sha256: downloaded, verified against it (a mismatch is an error, so a half-published deploy never runs a wrong model), cached, and all older versions deleted. Offline with a cached model: the cached `meta.json` copy is used. The model loads in the background (`createDispatcherFormalizer({ waitForModel: false })`: `available()` is false until `ready`, so the rules answer meanwhile); the status line reads "Model loading…" and then "Ready · model <version>" (+ "(cached)"). A failure shows one notice line and the rules stay in use; the saved setting is not changed.
- **Reading strategy** (ADR-009, spec 03 section 7.16): the setting `nxStrategy` (`hybrid` default | `neural` | `rules`; Settings > Understanding, "Reading strategy", persisted in `psys2.webchat.settings`, an unknown saved value falls back to the default) says who reads first when the encoder formalizer is chosen. Hybrid keeps the shipped answers and lets the model read only what nothing else understood; neural lets the model read first; rules never asks it. The published dispatcher model (`models/dispatcher/`, sha256 in `meta.json`) carries the NX heads, so one encoder pass serves the dispatcher and the strategy; the label tables and the trained worlds are in `meta.json` `nx`. With ORT paused (spec 06 ORT worker) or the model not ready the rules answer. The webchat trace shows "Read by" (model / rules) and "Reading strategy" for every segment.
- **Leniency settings**: "Spellcheck" sets policy `trySpell` and the session option `spell`; "Partial understanding" sets policy `acceptPartial` and the session option `partial` (spec 03 sections 7.9 and 7.10). The reply tells what was corrected (`(I read "yes" as "eyes")`) and what was ignored (`I understood only part of that: I did not use "..."`).

### Performance (PERF)
Measured with `scripts/perf-webchat.mjs` (headless Chrome, 390x844, 4x CPU throttle; puppeteer-core from a scratch install, see the script header).
- **Stage timing**: `src/formalizer/perf.mjs` keeps one record per top-level `DialogSession.send`; the reply carries it as `reply.perf = { total, stages: { name: { n, ms } } }` (stages are inclusive: `formalize`, `encoder`, `predict`, `ort`, `tokenize`, `validate`, `seed`, `check`, `normalizer`, `lenient`, `discourse`, `interpret`, ...). The webchat adds `engineMs`, `render`, `effects`, `totalMs`, shows the stages in the trace ("Timing"), pushes every record to `globalThis.__psys2Perf` and, with `?perf=1` in the URL, draws them in an overlay. Nested sends (scratch sessions) do not open records.
- **Validator seeds** (root cause of the slow encoder setting): `check` used to build a scratch session and replay the last six messages for every candidate (about 40 candidates per message, each replay re-detecting the language through the browser API). The seeded session is now built once per context (`seed`) and every check works on `DialogSession.forkForValidation()` (a copy of the interpreter session: memory overlay, world state, form state). Replays use language `en`. Readings are identical (test `tests/perf-fork.test.mjs`, and the operational set in encoder mode gives byte-identical replies).
- **Best effort with loose words** (`bestEffort`, session option, `RUNTIME_DEFAULTS.bestEffort = true`, webchat checkbox "Best effort with loose words", on by default; the `DialogSession` library default is off so that unit tests keep exact answers): when a message is ONE clause that nothing read (rules, spelling, partial understanding, normalizer, discourse all failed), the dialog builds a sentence from the content words and executes it, saying "I took that as: ..." (spec 03 section 7.15). `send(text, { bestEffort })` overrides per message; `sessionOptions(settings)` passes the flag, so the webchat and the evaluators share it. A/B in the evaluators: `--best-effort on|off` (`scripts/eval-operational.mjs`, `scripts/eval-dialogues.mjs`, reported in `config.policy`), and `scripts/eval-loose-words.mjs` runs every row with the flag off and on.
- **Fast path** (session option and webchat setting `fastPath`, default on in the webchat, off in `RUNTIME_DEFAULTS`; evaluation modes `encoder+fast`, `encoder+n1+fast`): in the encoder setting, a single-clause message (no `, ; :` and no connective) that the rules read as ONE segment completely, without spelling correction or ignored words, and whose readings the interpreter accepts on a copy of the session, is answered by the rules without running the model. A message with several clauses (`and`, `then`, commas ...) is also eligible (up to four segments): the rules must read every segment completely, and one dispatcher pass for the segmentation (`quickSegmentation`) must cut exactly where the rules cut, with the same world per segment; otherwise the normal path runs. Everything else goes through the dispatcher and the validator as before.
- **Start-up order (PERF round 3).** Background work (the sliced rule compilation, the warm-up sentences, the Romanian rules translator warm-up, the normalizer idle load) steps aside while a turn runs and for 500 ms after it (`userFirst`), so a message never waits behind it and a long synchronous chunk never starts right behind an answer. The warm-up marks its milestones with `performance.mark('psys2:<name>')` (`session`, `hint`, `warm-start`, `rules-compiled`, `warm-rules`, `warm-translator`, `dispatcher-ready`), printed by `scripts/perf-webchat.mjs`.
- **The normalizer loads when needed (decision f).** The ~95 MB normalizer is never fetched at page load. It loads the first time a message fails validation and the validator asks for a rewrite (the provider answers `not_ready` and starts the download; the rules answer meanwhile), after 30 s of idle time on a fast link, or on request (Settings > Models "Load now", or switching "Simplify phrasing" on). It is not fetched in the background when `navigator.connection.saveData` is set or `effectiveType` is slower than `4g`; Settings > Models then says the helper model loads when needed. The validator only asks for rewrites when no segmentation has a complete reading (spec 03 section 7.13).
- **Start-up**: models load after the page is usable (the hint message is shown), a scratch session warms the rules (pattern compilation, vocabularies) and then the model; `docs.reader` analyses its sample document once per page.
- **Thinking indicator**: on Send the message appears at once and the input clears; a "thinking... 0.8 s" bubble counts up live; each answer shows "answered in 340 ms".

### Phrase log (webchat Settings)
Collects every sentence a human typed or dictated, so real training data can be gathered. Implemented by `docs/webchat/ui/phrase-log.mjs` (pure functions plus a localStorage store); nothing in `src/` changes, the record is built from what `session.send()` returns.
- Record per user message: `id`, ISO `time`, `text` as typed or heard, `mode` (`typed` | `voice` | `chip`), `source` (`human`, or `chip` for example and suggestion buttons, which are not human phrasing), UI `lang`, `english` (the translation, when `reply.lang` is not `en`), active `tab`, `segments[]` (`text`, `status`, `world` and `pattern` from `segment.match`, `unparsed`, `strategy`; status comes from the answers addressed to the segment's wires), `unparsed`, `formalizer` (`reply.trace.formalizer.used`).
- Storage: localStorage key `psys2.webchat.phrases`, every access in try/catch, capped at 5000 entries (oldest dropped). On by default; the setting `logPhrases` ("Keep a log of my phrases (stays in this browser)") turns it off.
- A phrase is logged when it is sent (record with no outcome yet) and completed when the reply arrives, so a slow, failed or interrupted answer never loses it (RD7); the store merges with what other pages of the same browser wrote instead of overwriting it; a reply of an unexpected shape still yields a record. Test: tests/webchat-phrase-export.test.mjs (headless Chrome, needs `PUPPETEER_CORE`).
- Settings section: counts, filter (all / not understood only / voice only), scrollable list (newest first) with mode, world, status and per-entry Delete, Export JSON (`psys2-phrases-YYYYMMDD.json`, every field of every record, see Feedback below; every typed or spoken phrase is included, button presses only when "Include button presses in exports" is ticked), Clear with an inline confirmation (no browser dialogs).
- Voice commands: `ui.shell` pattern `ui.phraseLog` ("show my phrase log", "export my phrases", "how many phrases have I said?") emits the effect `phraselog { what: show | export | count }`, which the host carries out.

- **Feedback (FB).** Under every answer, next to Trace: a thumbs-up and a thumbs-down (`ui/feedback.mjs`, `aria-pressed`, tooltips "Good answer" / "Not what I wanted"); one vote per answer, changeable, a second click on the same button clears it. The thumbs-down opens an inline form: reason chips (wrong action, wrong thing / object, wrong place / value, did too much, did too little, wrong tab / world, misheard (voice), too slow, other), "What did you want?" (optional text) and, on the latest answer, "Show me the right result", which restores the session snapshot taken before that message (one snapshot is kept) and waits for the correction. The vote is stored in the phrase-log record as `feedback: { vote: 'up' | 'down' | null, reasons: [], wanted: '', correction: <id of the next accepted message> | null, undone?, spoken?, time }`; the record also carries `detail`: per segment the text, world, pattern, strategy, candidate worlds with scores, the SOP Lang wires, plus the answer, effects, timings and `state: { before, after }` (FNV-1a hashes of the session state), so a reviewer can replay the turn. The next message after a thumbs-down whose reply is fully supported and not complaint becomes the `correction` link. The spoken "that is wrong" / "nu asta am vrut" (spec 11 section 13, `reply.feedback === 'negative'`) sets the thumbs-down on the previous answer and opens its form; the complaint message keeps the older flag `feedback: 'negative'`. History marks each vote (up / down) and has the filters "Not what I wanted" and "Good answers". "Copy as text" is gone; **Export JSON** writes one `psys2-phrases-YYYYMMDD.json` (`{ format, exported, count, records }`, every field of every record) through the share sheet where the browser offers file sharing (phones) and a download otherwise. The learning loop (`scripts/learn-from-logs.mjs`) reads the JSON and the older JSONL: a thumbs-up is a self-validated example with the margin rule waived (structural checks stay), a thumbs-down is never self-labelled and becomes a review item with priority 0 when it has a `wanted` text or a correction (priority 1 otherwise; `thumbs_down` carries reasons, wanted, correction id and text), and the report counts the thumbs. Tests: `scripts/test-webchat-ui.mjs --only feedback`, `tests/phrase-log.test.mjs`, `tests/learn-logs.test.mjs`.

### Debug view per tab (DBG)
Settings > Developer has the switch **Developer mode** (`settings.devMode`, off by default, remembered). On, a thin header row under the tab strip carries a **Debug** button for the open tab (it follows the selected tab, tooltip "Debug this world"). It opens a full-screen modal built like the Settings modal (same classes, close button, Esc, focus trap, one history entry so that Back closes it) with six sections:
- **Commands**: generated from the loaded world (`engine.set`): patterns grouped by the operation they emit (`action=` of the request), each with id, priority, examples and a **Try** button that puts the example in the input; canonical examples; request shapes; a search box.
- **Last turns**: the last 20 turns that touched the world, newest first, each expandable: input, mode and end type, languages and translation, spelling corrections, the readings tried (pattern, complete or partial, refusal, candidate worlds with scores), the SOP Lang wires with syntax colouring (`colorSop` in `ui/trace.mjs`), operations with arguments, the reply, timings per stage, the stop or watchdog outcome, and the whole `renderTrace`.
- **Dry run**: `DialogSession.dryRead(text, { detail: true })` returns, besides `{ complete, segments, reason }`, `detail: { english, language, readings: [{ text, world, pattern, strategy, unparsed, partial, ignored, candidates, wires }] }`; it works on a fork of the session, so nothing is executed and the state hash is unchanged (the view shows the hash before and after). It also says whether the voice end-of-turn detector would send the phrase.
- **State**: the world's state as a collapsible JSON tree with the paths changed by the last turn highlighted, and the ASTRA view (discussions of the tab, instances, active discussion, focus, entities, recent worlds).
- **World**: manifest, imports, legend types and keys, lexicons with word counts and words, operations, templates, counts and `coverage.md` (copied by `scripts/build-webchat.mjs` to `worlds/<id>/coverage.md`, fetched on demand, not part of `index.json`).
- **Models**: dispatcher and normalizer (version, status, source, load time), the ORT worker (`globalThis.__psys2Ort`: restarts, requests, timeouts, aborts, lanes, sessions) and the last model calls for the world (input, output, ms).
Every section has **Copy** and **Export JSON** (share sheet where available, else a download); each turn can be copied or exported alone, and the phrase log shows a "debug dump" link per message while developer mode is on.
**Cost.** `docs/webchat/ui/debug.mjs` is imported dynamically only when developer mode is on; with it off nothing is downloaded, recorded or kept (switching it off destroys the module and its data). On, it keeps a ring buffer of the last 200 turns (the replies by reference, the state only as hashes, plus one full state snapshot of the last turn for the diff). Tests: `tests/webchat-debug.test.mjs`, `scripts/test-webchat-ui.mjs --only debug`.

### Turn lifecycle: one message at a time, Stop, watchdog, bounded stages (HANG + STOP)
A turn must always end, whatever the input, the CPU or the browser. Implemented by `src/formalizer/guard.mjs` (the turn guard), `DialogSession.send/snapshot/restore` and `docs/webchat/app.mjs`. User priority (2026-11-09): a few seconds are fine, a turn that never finishes is not.
- **One turn at a time, with a visible queue (MIC2).** Exactly one turn runs. While it runs, typed and spoken messages (Enter, a voice phrase that ended, an example chip) are not lost and not blocked: each becomes a chip above the input, in order, with an x that drops it; the mic shows a counter of the waiting messages (`host.queue` lists, drops and clears them; `host.turnState()` reports `{ running, queued, speaking, mic }`). They run one by one as soon as the turn ends. Typing and listening never stop; only sending waits. Stop ends the current turn and asks "Drop the N waiting messages too?" (Keep is the default and applies after 6 s). A queued bare yes/no whose question was already closed (the previous answer does not end in a question mark) is shown greyed with "skipped: the question was already answered" and not sent. The phrase log record keeps the wait as `queueMs`.
- **Stop.** While a turn runs the Send button is the Stop button (square icon, `aria-label="Stop"`, type `button` so that Enter never presses it). Stop aborts an `AbortController` whose signal is passed to `session.send(text, { signal, hardMs, softMs, undo })` and from there through every stage (see the guard). The host takes `session.snapshot()` (interpreter session, discourse memory, recent worlds, counters) before the message, and on Stop or timeout calls `session.restore(snapshot)` and re-applies the full world state to the tabs, so the session is as it was before the message. The reply is "Stopped.".
- **Watchdog.** A turn has a hard limit of 8 s by default (`LIMITS.watchdogMs`, configurable 2 to 60 s) measured from Enter. At 65 % of it (soft deadline) searching stages stop and keep their best result, so the normal outcome is the best reading found so far, answered a little late. At the limit the turn is aborted as with Stop and the answer is "That took too long, so I stopped. Try a shorter request." A host backstop 1.5 s later ends the turn even when the engine promise never settles. The stage the turn was in goes to the trace (the bot message has a Trace toggle) and to the phrase log.
- **Phrase log.** A stopped or timed-out phrase keeps its record and gains `outcome` (`stopped` | `timeout`), `stage` and `ms`; the export carries `outcome` and `stage`, and the "not understood only" filter includes them.
- **Turn guard** (`guard.install/check/soft/abortable/release`). `check(stage)` throws `TurnAborted` (`reason` `stopped` | `timeout`, `stage`) when the signal fired or the hard deadline passed, and is sticky. It is called by every `perf.time`/`perf.timeSync` stage, at the start of every rule `formalize` and clause read, in the interpreter (operation context calls and wire charges; `TurnAborted` is never turned into an operation error) and per word in the spell corrector. `soft()` is true after the soft deadline: the leniency, partial window, best effort and validation (segmentation, merge/split repair, normalizer, spelling variants) loops stop and keep what they have. `abortable(promise)` races an external await (language detection, translation, encoder, normalizer) with the signal and the deadline. The leniency stage also has its own budget, `LENIENT_BUDGET_MS` (3000 ms), shared by all its candidates. A caller that swallows an error cannot hide an abort: `send` checks the guard once more before it returns.
- **Host awaits are bounded.** `withDeadline(promise, ms, { signal, label })` settles within `ms` whatever the promise does. Every host effect runs under it (`TURN_LIMITS.effectMs`, 3 s) and so do the browser language detector (availability 1 s, detection 1.5 s) and translator (4 s). The language detector instance is never awaited while its model downloads: the rules detect the language until it is ready (a pending `create()` used to be returned to every later turn).
- **Cost.** Spelling variants build restricted world views (`restrictedSet`); they are memoized per (set, worlds), because each view owns the vocabulary and lexicon indexes (building them per candidate text made a one-typo message cost 3 s instead of 1.5 s).
- **Tests.** `tests/turn-guard.test.mjs` (abort, deadlines, restore, soft degrade, fuzzed turns); `scripts/fuzz-turns.mjs` (thousands of noisy turns from every evaluation set in Node, every turn must settle in the budget); `scripts/test-webchat-turns.mjs` (headless Chrome, 4x CPU throttle: the 2026-11-09 session, Stop restores state, Enter during a turn, a never-settling turn ends at the limit, 200 random messages; `tests/webchat-turns.test.mjs` runs a short version when `PUPPETEER_CORE` is set).
- **Model calls are bounded and the model host recovers (HANG2).** onnxruntime-web runs in our own module worker (`docs/webchat/ui/ort-worker.mjs`, one worker per lane: dispatcher, normalizer) behind `src/formalizer/ort-client.mjs`, not in ORT's `proxy = true` mode: that proxy transfers (detaches) input buffers, so the normalizer's second decode step threw "ArrayBuffer is detached" and the proxy then stalled every later call until the 8 s watchdog (stage `ort` / `encoder`). The client copies inputs, gives every call a deadline (dispatcher 2.5 s, normalizer graph 3 s by default, always clipped to what is left of the turn) and the turn's abort signal, and tells the worker to cancel; a queued job is dropped, and a running job that has not stopped 1.5 s later (`graceMs`, default 1500 ms) gets the worker terminated and re-created, its sessions reloading from the Cache API, so the next turn works. A timed-out call degrades (encoder: the rules answer; normalizer: no rewrite). The normalizer decode also stops at input length x 1.5 + 8 steps and at its own deadline (4 s). `formalizer: rules` never creates the client, the worker or a session. **Time limits** are defined once in `src/dialog/time-limits.mjs` (default, minimum, maximum of each) and edited in Settings > Developer > Time limits (`settings.timeLimits`, in seconds in the UI, clamped, applied live because every consumer reads the live `LIMITS` object per call or turn): turn watchdog 8 s (2 to 60), dispatcher call deadline 2.5 s (0.5 to 30), normalizer call deadline 3 s (0.5 to 30), worker cancel grace 1.5 s (0.1 to 10), leniency budget 3 s (0.5 to 30; `LENIENT_BUDGET_MS` in `src/dialog/index.mjs` is only the default). Tests: `tests/ort-client.test.mjs`, `tests/time-limits.test.mjs`. **Restart budget and device speed (FREEZE 5).** At most 2 worker restarts per 5 minutes (`restartBudget`); a third one pauses the models instead: the worker is terminated, sessions are not reloaded, every model call fails at once with `OrtPaused`, so the rules answer, and Settings > Models shows "Models paused" with the reason and a "Resume models" button (`client.paused`, `client.resume()`, `stats.pauses`; the page also gets a `psys2-ort-paused` event and a toast). A quick calibration at load (`measureDeviceSpeed`, best of three runs of a fixed loop against a reference time, clamped to 1..8) gives a speed factor that multiplies every call deadline and the cancel grace, so a slow or throttled device is not mistaken for a hung worker (a hung worker restarts the ~160 MB of sessions, which loads the CPU further). Test: `tests/ort-budget.test.mjs`; the soak (`scripts/soak-webchat.mjs`) asserts at most 2 restarts.
- **The pipeline runs in a Web Worker (COMPUTE-BUDGET, see "Engine worker" below).** The older cooperative guard stays inside the worker as the first line; the page-side watchdog terminating the worker is the last.

### Engine worker: the engine off the page thread, a watchdog that terminates, no repetition (COMPUTE-BUDGET 1, 3, 5)
User decision 2026-11-10: infinite loops are prevented on principle, not one bug at a time. `docs/webchat/ui/engine-worker.mjs` (a module worker) holds `DialogSession`, the formalizers, the translators (the rules translator; the browser Translation API and language detector exist on the window only, so the worker asks the page for them, see "Browser translator bridge" below), the interpreter, the world operations and the dispatcher / normalizer runtimes. The page thread (`app.mjs`) keeps the UI, speech, effect rendering, storage and the phrase log. `docs/webchat/ui/engine-client.mjs` is the page side.
- **Protocol** (structured clone only): page to worker `init | send | dry | observe | setWorldState | setStates | restore | settings | option | abort | prepare | candidates | warm | ort-resume | ort-restart`; worker to page `{ type: 'res', id, ok, value | error }`, `{ type: 'evt', name, data }` (`stage`, `dispatcher-status`, `normalizer-status`, `model-source`, `progress`, `ort`, `ort-paused`, `rules-compiled`, `warm`) and `{ type: 'spawn-ort', lane, port }`. The ORT workers belong to the page: the engine worker asks for one per lane and talks to it through a `MessageChannel` that the page bridges (`ui/ort-host.mjs` takes `globalThis.__psys2OrtSpawn`), so terminating the engine worker also stops them.
- **`session` on the page** is a proxy with the methods the UI used: `send`, `dryRead`, `observe`, `setWorldState`, `state()` (the committed state of every world, read only, refreshed by every reply), `snapshot()` / `restore()` (a token `{ id, state, meta }`; the worker keeps the last 24 engine snapshots by id), `applySettings`, and `nx` / `formalizer` accessors. The reply carries `sk` on every wire (short keys; the legends stay in the worker), and the usage / detection lists of the translator and `budget` (ticks per site, when the step budget is present). Every turn also carries the current settings.
- **Turn watchdog.** The page's watchdog (`LIMITS.watchdogMs`, Settings › Developer, default 8 s) aborts the turn; the client then posts `abort` and, when the worker has not stopped within the grace (300 ms: it is inside synchronous code), **terminates it** and starts a new one from the last committed world state (the state before the turn, the message counter and the **conversation memory**: `meta.memory` = `DialogSession.memoryJSON()`, plain JSON of the discourse state (frames, pending question, actions, topics, last answers), the ASTRA discussions and instances, the recent worlds and the last game; the worker returns it with every turn and restores it with `restoreMemory`, so "and from Berlin?" and "undo that" still work after a restart). The turn answers "That took too long, I stopped it." and the stage the worker reported last (it posts every `guard` stage change at once, even from inside a loop) and the input go to the console, the phrase log (`outcome: timeout`, `stage`) and the debug view. Stop uses the same path, so Stop always works (a turn stuck in a loop ends in under 100 ms on screen; the worker is replaced in the background; a new request waits for it). A replacement worker loads the models from the Cache API in the background; the rules answer meanwhile. After 3 failed starts in a row the engine stays down (no restart loop).
- **No repetition.** The client remembers for the session every input (normalized text, lower case, single spaces + the open tab) whose request needed a kill, ended in `BudgetExceeded` or crashed the worker. It is never run again: not by the next identical message (the stored outcome is answered: "I stopped that same request earlier because it took too long, so I did not try it again. Please word it differently."), not by a dry run (the voice end-of-turn check and the noise classifier get `known-slow`), not after a worker restart, and the client never re-sends a request by itself. Every retry path inside a turn has a fixed maximum: `_formalize` is called at most 4 times per message (`tests/formalize-calls.test.mjs`).
- **Evidence from real browsers.** A `PerformanceObserver('longtask')` records every main-thread task over 200 ms with the host stage (`thinking`, `render`, `effects`, `idle`) and, while the engine runs, the engine stage: into the phrase-log record of the turn (`longtasks`) and into `window.psys2.longTasks`. The reply's ticks per site (`reply.budget`) go into the record (`budget`, also in `detail`). The phrase-log export (`toJSON(list, { diagnostics })`) has a top-level `diagnostics` object: `longTasks`, the engine counters (`starts`, `crashes`, `sends`, `dryRuns`, `refused`, the `kills` with reason, stage, site, input and tab) and the ORT counters. The debug view shows the same under Models ("Engine worker") and the step budget under Timing.
- **Fault injection (tests only).** With `?psys2test=1` in the page URL, `window.__psys2Fault = { <exact text>: 'op' | 'matcher' | 'translator' }` makes the worker spin in a world operation, in the rules matcher or in the translator when it handles that text. Without the query parameter nothing reads the table. `scripts/test-webchat-budget.mjs` (and `tests/webchat-budget.test.mjs`) check, for each fault: echo of the typed message under 100 ms, no heartbeat gap over 500 ms, the turn ends at the watchdog, the worker was replaced once, the next message works, and the same input (also upper case, extra spaces, a dry run) is not run again; plus Stop during a loop, hands-free voice and the evidence.
- **Browser translator bridge.** Before the engine moved, the page's `createSwitchTranslator` used the on-device Translator and LanguageDetector on the critical path (400 ms per call, then the rules; HANG3). The worker keeps that code (`ui/translation.mjs`), with a remote backend: `{ type: 'bt', id, op: 'translate' | 'detect', text, from?, to? }` to the page, `{ type: 'bt-res', id, ok, value | error }` back. The page answers from `createBrowserBackend()` (the HANG3 machinery: `create()` once per pair, never awaited beyond 400 ms, cooldown, background download); the worker waits at most 700 ms, then the rules answer (`usage[].reason` says "page translation timed out"). The checker (numbers, names, negation, question form) runs in the worker. The page reports which APIs exist at start (`init.browser = { translator, detector }`); without them no message is sent. A page that does not answer never stalls a turn.
- **Translator as a fallback (RO-TRANSLATE-FALLBACK, user 2026-11-11).** The selected language still decides what the user sees and hears; the on-device Translator is only a safety net inside the turn, and rules and templates always come first. `createSwitchTranslator` gives `fallbackMode()`: `'fallback'` for the strategy `auto` (the default: rules first, the Translator for what they could not do), `'primary'` for `browser-api` (the old order: the Translator, then the rules) and `'off'` for `rules`. In `'fallback'` mode:
  - **Input** (`DialogSession._send`). A Romanian message is read through the rules. The reading is *poor* when the trouble points of its segments are above zero: a clause not understood (3 points), a part not used (1 each), a best-effort "I took that as" (2), the message left in Romanian by a rules translator that reported unknown words (2). A poor reading with a Translator available (`canTranslate('ro','en')`, turn not past its soft deadline) asks `viaBrowser(text, { from: 'ro', to: 'en' })`: the Translator only, bounded by the bridge deadline (700 ms from the worker, 400 ms in the page), checked by `checkTranslation` (numbers, names, negation, question form; a Romanian statement that starts with "e", "este", "are" is not a question without "?"). The session goes back to its state before the first reading and reads the clean English with the English rules; the second reading replaces the first only when it has fewer trouble points, else the first is put back unchanged (`trace.via = 'translator-in'`, `trace.firstReading`). A Translator that is absent, switched off, late, failing or rejected by the checker leaves the first reading and costs nothing beyond the bounded call.
  - **Output** (`translateParts`). A run of the English reply the rules and templates cannot put into Romanian (unknown words, an English word left) goes to `viaBrowser(run, { from: 'en', to: 'ro' })`, accepted when the checker passes and no English word is left (`route 'translator-out'`). Our own English reading of the user's words ("I took that as: ...") and the examples are treated the same way. What nothing can translate becomes the fixed Romanian line "Nu am încă o formulare în română pentru acest răspuns." with the user's quoted words (`route 'ro-generic'`): a Romanian session never shows English. When the rules translated everything the route is `'rules-translate'`. At most 6 Translator calls per turn. The plain `createTranslator()` (CLI, tests) has no fallback mode and keeps the RD5 behaviour (an untranslatable reply stays English as a whole).
  - **"No English word left" (RO-LEFTOVERS).** `translator.leftovers(text, 'ro')` (`englishLeftovers`) lists every word of the rules translator's English lexicon, and its regular forms (`-est`, `-er`, `-ing`, `-ed`, `-ly`, plural), that Romanian does not also know; quoted text, names and numbers are never leftovers. The frequent replies that ended as the fixed line are templates in `replies.en-ro.mjs` (distance, borders, chess help, key signatures, the guessing game's list, the examples of the avatar help through the canonical Romanian examples); "bar chart" is written "grafic cu bare".
  - **Host strings.** `DialogSession.observeIn(obs, { language })` is `observe` for a host that shows the reaction to the user (the engine's own chess move): the text goes through the same outbound path (`textEnglish` keeps the English, `via` the routes). The engine worker uses it.
  - **Trace and phrase log.** Every route is recorded in the translator `usage` list (`via`, `strategy`, `fallback`, `reason`: shown in the trace), in `reply.trace.via` / `reply.trace.replyVia`, and in the phrase-log record as `via: ['translator-in' | 'translator-out' | 'rules-translate' | 'ro-generic']`, so a missing template can be added later; the fallback does not replace adding it.
  - **Quotes.** Romanian replies quote with „…”; a refusal that quotes a word the user typed ("There is no dragons tab.") quotes the user's word (`„dragoni”`, found through the translation alignment, `userWordMap`).
  - **Tests and measurement.** The harness fake offers ro to en and en to ro (`pairs`, a small table `FAKE_RO_EN` / `FAKE_EN_RO`, then the rules). `tests/ro-fallback.test.mjs` and `tests/ro-fallback-fixes.test.mjs` cover both directions, both reasoners, the absent, wrong, late and hanging Translator, and the small fixes; `scripts/measure-ro-fallback.mjs` runs the Romanian operational set before and after with an oracle Translator and reports understanding, English replies left and the added time.
- **On-device translation model (MT-SERIOUS, user decision 2026-11-12).** Chrome on Android, Firefox and Safari have no Translator API, so the translation layer has an engine of its own. The order is (a) the browser's Translator for a pair it supports (`Translator.availability()` per pair, asked once, bounded), (b) otherwise the on-device model, (c) nothing else (the call fails and the turn says so). Nothing is generated by a large language model: the engine is **bergamot-translator 0.4.9** (Mozilla's Marian student models in WebAssembly, MPL-2.0, vendored under `docs/webchat/vendor/bergamot/`), the models are Mozilla's Firefox Translations models (MPL-2.0), listed in `vendor/bergamot/registry.json` (`scripts/build-mt-registry.mjs`, from Mozilla's public model registry; a language is listed only when both directions with English exist; per direction the smallest released model; sizes are the gzip sizes). The bucket sends CORS headers, so the page downloads the files from it directly; nothing of the models is in the repository.
  - **Host** (`ui/mt-host.mjs`, pure of `node:*` and the DOM). `createMtHost({ registry, fetchFile, spawn })`: `ensure(lang)` downloads the six files of a language (model, shortlist and vocabulary, both directions), starts the engine in **its own classic worker** (the vendored `translator-worker.js`, protocol `{ id, name, args }`), loads both directions and reports `{ phase: idle | downloading | loading | ready | error, done, total }` through `onState`; `translate(text, from, to)` never waits for a download (it rejects when the language is not ready) and has a per-call deadline (2.5 s); calls run one at a time; a call that misses its deadline terminates the worker (WASM cannot be interrupted) and the language needs `ensure` again (the files come from the cache). Node tooling uses the same host (`scripts/lib/mt-node.mjs`).
  - **Page** (`ui/translation-ui.mjs`). The page fetches with progress, keeps the gzip in **Cache Storage** (`psys2-mt-v1`), gunzips (`DecompressionStream`) and checks the model file's sha256 against the registry. The model of a language is downloaded **lazily, when the language is selected** (selector, Settings, or a saved language at start, after the first paint, `setTimeout 0` after the engine booted); English selected: no request, no worker. While it downloads a banner under the header says "Downloading the translation model for Romanian (30 MB)… 42%" with a progress bar, and a failure shows the reason with a Retry button. A message sent meanwhile waits in the thinking bubble ("downloading the Romanian translation model (30 MB)… 42%", stoppable, at most 3 min); the turn clock (watchdog) starts when the model is ready, like after an engine restart; if the model could not be made ready the message is answered with what exists (the rules for Romanian, the English reply otherwise) and a note says why.
  - **Layer** (`createBrowserBackend({ mt })`). The page-side backend answers the worker's `translate` request with the native Translator when it supports the pair, else with the model; a native translator that is still preparing hands over to a ready model. The worker's remote backend gets a longer deadline (3.5 s instead of 0.7 s) when `kinds.mt` is set. The engine reads and writes **any language code**: only Romanian has rules (`translator.rules.supports(from, to)`); for any other language `_sendCore` reads through `viaBrowser(text, { from, to: 'en' })` (a failure leaves the message as typed: not understood) and `translateParts` sends every run to the model (the stub `NO_RULES`); a reply the model could not produce stays in English, never the Romanian fixed line (that line is Romanian only). The checker keeps its numbers, names (a name is kept when the target has it or a word that starts like it; skipped for German source, whose nouns are capitalised, and for non-Latin targets) and "?" for every language; negation and question-word tables exist for English and Romanian only.
  - **Language list** (`ui/language.mjs`, `listed()` of the layer). Every registry language (and, in a browser with the Translator, every language it supports in both directions) is a candidate; one is listed in the selector only when at least **80 %** of a sample of the English operational set is read right after machine translation English to language to English by the on-device model (`scripts/mt-quality.mjs`, judged like every operational run; result in `vendor/bergamot/quality.json`, shown with its number in Settings > About); English and Romanian are always listed (Romanian has its own rules). Settings > Language has "Show every language of the translation engine" for the ones below the gate (labelled with their number). The language code is any `xx`/`xx_yyyy` of the registry; recognition and synthesis use its BCP-47 tag (`zh_hant` is `zh-TW`, `tl` is `fil-PH`); where the browser has no voice for the language a note says once that answers are written and typing works.
  - **Tests.** `scripts/test-webchat-phone.mjs` is the Chrome "phone" mode (`browserApis: { translator: false }`: no Translator, no LanguageDetector; the bucket's files are served from `PSYS2_MT_CACHE` when set): lazy loading, Romanian turns at 4x CPU, Cache Storage reuse after a reload, a language without rules (German), an unreachable bucket. `tests/mt-layer.test.mjs` covers the order, the deadline and restart, the failed download and the checker with a fake worker; the fake Translator of the harness stays for those and for the desktop rows. Measuring: `scripts/mt-read.mjs` (reading on `operational-ro`), `scripts/mt-replies.mjs` (replies), `scripts/measure-mt-chrome.mjs` (load and per-sentence time at 4x CPU), `scripts/mt-quality.mjs` + `scripts/mt-quality-merge.mjs` (the language gate); results in `training/results/mt-serious-2026-11-12.md`.
- **Restart: the turn clock starts when the worker is ready (COMPUTE-BUDGET E).** The replacement worker is started at kill time (`respawn()`, also after a crash) and kept warm. A message that arrives while the client is not settled (a replacement is starting, an abandoned request is still being ended, no worker runs) shows "restarting…" in the thinking bubble and waits (`engineClient.settled()`; further messages queue behind the turn as usual); the watchdog, the backstop and the "thinking… s" clock start only when it resolves, so start-up (loading and compiling the rules, slow on a throttled phone) is never charged to the turn. Stop during "restarting…" ends the turn as stopped. Start limit `LIMITS.startMs` (Settings › Developer › Time limits, default 60 s, 10 s to 300 s): a worker that is not ready within it is terminated once and the engine stays down (`stats.startTimeouts`, event `engine-down`); the waiting message then ends with the distinct visible error "The engine could not restart. Please reload the page." (`data-engine-down`), a `detail.engineDown` record in the phrase log and a `engineDown` entry in the debug view. Never a chain of kills and restarts. Test: `scripts/test-webchat-budget.mjs --only restart,stop` at `--throttle 6` and `1` (the test hook `window.__psys2StartHang` makes the replacement never become ready).
- **Main-thread cost per turn (COMPUTE-BUDGET E).** `scripts/perf-turn-cost.mjs` measures CDP `TaskDuration` (all main-thread tasks including style, layout and paint) per message at 4x CPU. Findings: (1) the avatar's DiceBear SVG animates inner nodes (main-thread repaint every frame, about 60 ms per second at 4x), so `.p2-rest` (set on the root from the start of a turn until 3 s after it) switches those animations off (`animation: none`; a paused animation still costs); (2) the draw tab's canvas was a fixed 2000x1400 px that was redrawn and committed on every animation frame: its backing store now follows the displayed size times the device pixel ratio (capped at 2000 px, from a `ResizeObserver`, no layout read per frame) and a hidden tab paints nothing; (3) the robot's float animation repainted the page: `contain: layout paint; will-change: transform` on `.p2-robot`. Per-turn style recalculation is about 20 ms and the veil toggles are not a measurable cost.
- **Build: versioned module graph.** A worker has no import map, so its imports are plain URLs and could pair a fresh module with a stale cached one (Pages sends `max-age=600`). `scripts/build-webchat.mjs` (`versionGraph`) gives every module of `lib/` and `worlds/` a version that covers its text and everything it imports (a Merkle hash over the static and literal-dynamic import graph; an import cycle is one unit) and rewrites every relative specifier in those generated files to `<specifier>?v=<version of the target>`. A module always loads the dependencies it was built with, in the page and in a worker alike, and an unchanged subgraph keeps its URL and stays cached. The page's import map and `window.__psys2Mod` carry the same versions for these files (one instance per module); `ui/` files and `app.mjs` keep a content hash. The worker imports `lib/` and `ui/` files through `globalThis.__psys2Url(rel)` (the page's versions, passed at `init`); the few `ui/` files it loads (`translation`, `dispatcher-host`, `normalizer-host`, `ort-host`) import nothing relative. `tests/build-versioning.test.mjs` (Merkle properties, every import of the build names its target version, no relative import in the worker's ui files) and `tests/webchat-freeze.test.mjs` (no module request without `?v=` from the page or its workers).

### Compute budgets: loops that cannot run away (COMPUTE-BUDGET)
Every loop has a generous, deterministic compute budget, and a computation that ran out of budget stops and is not repeated. User decision 2026-11-10 (a tab froze on every command). The turn guard (above) bounds time at cancellation points; the budget bounds work at every loop site, in ticks, so it is the same on every machine. The watchdog that terminates a worker (agent A, `docs/webchat`) remains the last resort for synchronous code.
- **Counter** (`src/dialog/budget.mjs`, browser-safe). `createBudget(limits)` returns `{ tick(site, n = 1), ticks, bySite, exceeded }`. `tick` adds `n` to the site and to the turn total and throws `BudgetExceeded` (`name`, `site`, `ticks`, `limit` = `'site'` | `'turn'`) when the site passes its limit or the turn total passes `perTurn`. The excess is sticky (`budget.exceeded`): every later tick throws again, so a `catch {}` that swallows the error cannot buy more work. `UNLIMITED` is the no-op budget.
- **Limits** (`src/dialog/budget-limits.mjs`): `perTurn`, `perSite` (default for every site) and `sites` (per-site overrides), in one config. A site's default is the larger of 10x the p99 of its ticks per turn and 2x the maximum, measured on the operational sets and the dialogues by `node scripts/measure-ticks.mjs` (table in the worker-log entry COMPUTE-BUDGET B), rounded up and at least 20 000; they are far above any real turn, so results do not change. Re-measure when a site is added.
- **The shared handle.** Loop sites call `budget.tick('<area>.<site>', n)` on the shared handle exported by `budget.mjs`, which forwards to the budget of the turn in progress (like `guard`; outside a turn it is a no-op). `DialogSession.send(text, { budget })` installs `opts.budget` (a fresh `createBudget()` when absent; nested replays join the outer turn), `dryRead` runs its own budget, and operations of worlds receive it as `ctx.budget`. A world helper that has no `ctx` (placement, layout, routing, solvers) and may not import reaches the same budget through the well-known global `globalThis[Symbol.for('psys2.budget')]` (the shared no-op-outside-a-turn handle, set when `budget.mjs` loads); a world file starts with `const budget = { tick: (site, n = 1) => globalThis[Symbol.for('psys2.budget')]?.tick(site, n) };` and then calls `budget.tick(...)` like core code.
- **Sites ticked:** `matcher.attempt`, `matcher.backtrack`, `rules.pattern`, `rules.readgroup`, `rules.sentence`, `normalize.fixpoint`, `spell.edit` (every edit-distance call: spelling, names, closest words), `dialog.formalize`, `dialog.lenient`, `dialog.spell`, `dialog.names`, `dialog.besteffort`, `dialog.capability`, `dialog.settle`, `discourse.{meta,fill,ellipsis,pronoun}`, `interpreter.visit` (wire charges: rule evaluation and inference chaining), `ops.call` (every `ctx` call of an operation), `translate.{tokenize,parse,clause,frame,np,render,items,segment}`, `soplang.{entry,wire}`, `wordpiece.{start,end}`, `voice.rec`, `dispatch.segmentation`, `dispatch.rewrite`, `normalizer.decode`; in worlds: `art.place` (crowd checks of every candidate spot), `art.np`, `diagram.{layout,route,place,solve,path,name,words}` (the engine's separation, force and crossing passes, arrow routing, the free-spot grid, the datalog solver and fixpoint, the path search), `reader.{np,pp,merge,id}`, `time.chain`, `music.stack`.
- **At the turn level.** `send` catches `BudgetExceeded` (and checks `budget.exceeded` after the turn, for stages that swallowed it), restores the session snapshot and answers `reply.tooComplex = true`, `reply.text = "That was too complex for me — try a shorter sentence."`, with `reply.budget = { ticks, top: { site: ticks, ... }, exceeded: { site, ticks, limit } }` (also in `reply.trace.budget`). A normal reply carries `reply.budget` too (ticks and the five busiest sites) for the trace and the phrase log. `dryRead` answers `reason: 'budget'` with the same `budget` block. The host records the input as budget-exceeded (no repetition, see the host side of this task).
- **Static enforcement** (`tests/loop-guard.test.mjs`, `scripts/lib/loop-scan.mjs`, `scripts/lib/loop-targets.mjs`; `node scripts/loop-violations.mjs` lists the offenders, `node scripts/audit-bounded.mjs` the leftover `// bounded:` comments). The test scans `src/`, every module of every world (`worlds/**/*.mjs` except `datagen.mjs` and `vendor/`) and `docs/webchat/ui/` (`docs/webchat/lib` is generated from `src`). The converted diagram engine (`worlds/diagram.sketch/engine/`, generated and not edited by hand) is checked differently: `scripts/convert-diagram-engine.mjs` inserts `budget.tick('diagram.*')` into its layout, solver, path and name loops and the test checks they are there; its regex loop is a `matchAll` and the regex test below scans it too.
  - **A comment is a claim, not a guard.** A `// bounded: <reason>` comment excuses nothing (the freeze of 2026-11-10 sat behind a false one: "regex exec with the g flag advances lastIndex"), and a test asserts that none is left. Every `while`, `do ... while`, `for (;;)`, a C-style `for` that is not a plain counting loop (the loop variable is assigned in the body, or the bounding collection grows), a `for (x of Q)` whose body pushes to `Q`, and every self-recursive function must call `budget.tick(` or be **verifiably finite** to the scanner: a loop whose body `await`s (it yields to the event loop every pass), a recursion whose self-calls all sit in callbacks that run later (`setTimeout`, `addEventListener`, `on...` handlers, promise callbacks), a recursion with a depth cap (`if (depth > N) return`, self-calls pass `depth + 1`), a `for ... of` over a collection the body does not grow. Anything else ticks (a tick costs about 10 ns). The one deliberate infinite loop, the fault-injection hook of the engine worker, is marked `loop-guard-allow` and listed in the test.
  - **Regex loops.** `while ((m = re.exec(s)))` (also do and for) is refused unless (a) it is converted to `matchAll` / `replace`, or (b) the regex provably cannot match the empty string (`minLen`: every top-level alternative must consume at least one character; groups, classes, escapes and quantifiers are computed, lookarounds, anchors, `\b` and back-references count 0, anything not provable fails), or (c) the body advances `lastIndex` on an empty match (`re.lastIndex++`, `+= n`, `= ... + 1`). A tick or a comment does not excuse it. A non-global regex driving a `while` is an endless loop and is refused; a regex the scanner cannot resolve to a literal in the file (`new RegExp(...)`) is refused. Also refused: `matchAll` / `replaceAll` with a regex that is not global (they throw). New code uses `matchAll`.
  - **Hot loops and limits.** Every tight index loop is ticked, so the per-site and per-turn limits in `budget-limits.mjs` are measured over the operational sets (`node scripts/measure-ticks.mjs`) including these sites; a site that is hot (several hundred thousand ticks in a turn) has its own entry.
- **Cost.** A tick is one function call and two additions (about 10 ns); a typical turn makes 5 000 to 10 000 of them (about 0.1 ms against a p50 turn of 15 ms in rules mode).
- **Tests.** `tests/budget.test.mjs` (counter, limits, sticky excess, shared handle, turn-level catch with restore, `ctx.budget` in an operation), `tests/loop-guard.test.mjs`.
- **Fake on-device translator in the browser harness** (`scripts/lib/fake-browser-apis.mjs`, installed by default by `openChat` in `scripts/test-webchat-turns.mjs`, so every browser script and `npm run test:browser` runs with it). The browser's own Translator and LanguageDetector exist only in a real Chrome, so the code behind them (the page-side backend, the bridge into the engine worker with its 700 ms deadline, `checkTranslation` for numbers, names, negation and question form) never ran in headless tests, and an endless loop there froze real pages. The fake installs `window.Translator` / `window.LanguageDetector` (and, with `shape: 'ai'`, the older `window.ai.translator` / `window.ai.languageDetector`), ro to en and en to ro (`pairs`, a small table of sentences, then the rules), with modes `success` (the English of the rules translator, run in node and exposed to the page, and the rules language detection), `slow` (later than the bridge deadline), `hang` and `wrong` (`empty`, `garbage`, `numbers`, `names`, `negation`, `punct`: a text that starts with punctuation, the shape that triggered the old loop). `scripts/test-webchat-budget.mjs --only ondevice` asserts for each: echo of the typed message under 100 ms, no heartbeat gap over 500 ms, no worker kill, the turn answered; success: the checker ran and accepted (first row: the exact old trigger "fă o casă verde și una galbenă", both houses drawn); slow: the rules translated after the deadline; wrong output: the checker rejected it with the right reason and the rules translated. `openChat({ browserApis: false })` leaves the page without the APIs.

### Busy state: veiled tabs (BUSY)
One source of truth in `docs/webchat/app.mjs`: `host.isBusy()` is true while a turn runs, while its host effects run (`effectsPending`) and while the answer is read aloud (`speaking`). `host.onBusy(fn)` subscribes. While busy every tab panel gets a light grey veil (`.is-busy::after`), `aria-busy="true"`, `inert` and a spinner in its tab header; clicks do nothing and are not queued. The chat input, the tab switcher, Settings and Stop stay usable; the map, diagram and chart tabs are not inert (their controls are disabled by CSS) so pan, zoom and scroll still work. Stop and muting cut the speech, abort the turn's `AbortSignal` (passed to tab effects as `ctx.signal`) and lift the veil at once. A speech that never ends does not hold the veil forever: it is lifted after `TURN_LIMITS.speakBaseMs + speakPerCharMs * answer length` (at most `speakMaxMs`); effects are already bounded by `effectMs` through `withDeadline`. Tests: `scripts/test-webchat-turns.mjs --only busy`.

### Spoken messages: natural end of turn (VOICE)
The browser's `isFinal` alone is not enough (Chrome keeps hands-free and `ro-RO` results interim for a long time, and stopping the mic dropped interim text). `docs/webchat/ui/speech.mjs` has its own end-of-turn detector on the interim text; the same behaviour for every language.
- **Pause timer.** Every change of the interim text restarts a timer (`VOICE_TIMING.plausibleMs`, 700 ms). When the text has been still: if it is *plausible* the message is sent (`pause-plausible`); otherwise the app waits until `waitMs` (1800 ms; hands-free `handsFreeMs`, 2500 ms) since the last change and sends anyway (`pause-timeout`). Plausible = the text does not end in a connector or a preposition (`endsOpen`: and, then, to, with, a, the, of, ... and Romanian și, apoi, la, cu, pe, ...) AND the dry run `DialogSession.dryRead(text, { language, signal, deadlineMs, detail })` finds a complete reading. FREEZE 4: the dry run is bounded and cancellable. It honours the `AbortSignal` at every cancellation point of the turn guard, runs with leniency off (no spelling variants, partial windows or best effort) and the rules translator only (never the browser translator), allows one in flight per session (a newer call cancels the older, which answers `cancelled`), and is skipped without any work for more than 25 words (`too-long`) or when no word of the text is in any world's vocabulary (`no-vocabulary`). `scripts/measure-dryread.mjs` measures its main-thread time on Romanian room talk; test `tests/dry-read.test.mjs`. EOT2: the dry run is complete only when the reading has every required argument (status `missing` or `ambiguous` is not complete: "play" asks what to play); `endsOpen` also holds a text whose last word is a command verb, a determiner or a number ("play", "draw a", "add 3"; a lone number is a complete answer), so these wait the long pause. A bare "play" that the long pause still sent is continued by the next utterance within 3 s.
- **Dry run.** `dryRead` formalizes the text with the rules on a fork of the session (`forkForValidation`), after the translation for Romanian, and checks that every segment is read completely (nothing unparsed, partial or ignored) and that the interpreter does not refuse a reading (`unsupported`, `error`). It never executes on the real session and touches no session state (language, discourse, counters). It runs under its own short turn guard (400 ms) and declines (`busy`) while a real turn owns the guard; the host also races it with `VOICE_TIMING.dryRunMs` and treats a miss as "not plausible". SOAK-BUSY: a settled answer (not `cancelled`, `deadline`, `busy` or `error`) is reused for 5 s (`DRY_CACHE_MS`) for the same text, language, active tab and session state (message counter and a revision bumped by `setWorldState` and `observe`), so the pause check and the NOISE classifier read a text once; the cached run always keeps its `detail`, which is stripped when the caller did not ask for it. Host rendering rules for long voice sessions: the mic and record pulses animate `transform` and `opacity` of a pseudo-element only (an animated `box-shadow` repainted the page every frame), the chat scrolls once per animation frame, the status line, send button and button labels are written only when their value changes, and the ring animation restarts on the next frame without a forced layout.
- **Browser final.** `isFinal` sends at once (`final`). One utterance is sent once: after a timer send the recognizer is restarted (hands-free) and a late final that only repeats the sent text, or starts with it, is dropped or reduced to its new tail.
- **Mic stop.** Stopping the mic sends the interim text unless a final arrives within `micStopMs` (300 ms) (`mic-stop`); a recognizer that ends on interim text without a final also sends it.
- **Visible and cancellable.** The interim text is in the input field; the mic button shows a countdown ring (`onPending`, SVG circle animated for the remaining ms) while a send is pending. Typing in the field, tapping it, or saying "stop" / "cancel" / "anulează" after a plausible sentence keeps the text in the field for editing and sends nothing (a lone cancel word with nothing pending is an ordinary message).
- **One at a time (HANG + STOP), now queued.** A spoken message that ends while a turn runs joins the visible queue (see "One turn at a time, with a visible queue"); while a turn runs the dry run declines, so such a message waits the long pause (2.5 s) before it is queued.
- **Recognition language (LANG-FIXED).** The recognizer's `lang` is the tag of the selected language (`ui/language.mjs`, `en-US` or `en-GB` by Settings > Voice > English variant, `ro-RO`), set at every start; nothing else sets it (not a reply, not a detection). On a change `speech.refreshLang()` restarts an idle hands-free recognizer (a single-shot one takes it on its next start). The tag the recognizer actually used (`speech.recLang()`) is stored in every voice phrase-log record as `recLang`, next to `selectedLang` (the selected language), so an export shows a mismatch at once. **Reply voice:** the answer is read with the voice that speaks the selected language (the chosen voice only when it matches the language; else the first voice of the tag); with none installed the utterance still carries the tag and the default voice speaks, and Settings > Voice says "No Romanian voice is installed on this device: answers are read with the default voice" (or names the voice in use). Tests: `tests/language.test.mjs` (unit), `scripts/test-webchat-language.mjs` (browser: ro-RO on every start across 30 turns with English-looking finals, an English typed message, a tab switch, a hidden tab, a worker restart and a page reload; symmetric English; the switch commands; the spy; the 09e replay).
- **Hands-free.** Recognition is still paused while an answer is read aloud and resumes the moment the speech ends (no 350 ms dead zone, so "Say yes to ..." can be answered at once); after a send the utterance is restarted at once.
- **Conversation mode (VOICE2).** One click on the mic turns the microphone on and it stays on (this is the old hands-free mode; the long press is gone). It restarts the recognizer on every `onend`, `no-speech`, `aborted` and network error (delay 150 ms, doubling after each failure up to 5 s; an end within 500 ms of the start with no result counts as a failure). After 6 consecutive failures it does not give up silently: the mic shows the paused state ("Microphone paused — tap to resume (reason)", `data-mic="paused"`, also in the status line and a note); a tap (`resume()`) listens again. A second click, or a stop command, turns it off. Settings, Voice: "Keep listening until I say stop" (`keepListening`, default on); off makes a click a single message. The mic button's `data-mic` is `off | listening | waiting | once | paused` and its title = aria-label says the state. MIC2 (reliable button): there is no long press. `speech.toggle()` acts at once: the visible state flips on the click (optimistic); after `stop()` the recognizer is aborted if `onend` has not come within 300 ms (`abortMs`); clicks within 250 ms of a flip are ignored (`debounceMs`); `starting` (until `onstart`) is its own state shown with a spinner ring (`data-mic="starting"`); a click while the answer is read aloud is a barge-in (the speech stops and the mic listens now); a recognizer that is still ending never blocks the next start. Every click is logged with the state before and after (`host.micLog`, Settings > Developer). Test: `scripts/test-webchat-voice.mjs` scenario `clicks` (50 random clicks with 1.5 s `onstart` and 2 s `onend`: state equals recognizer state, no click lost).
- **Stop commands.** Handled locally by `isStopMicCommand` (speech.mjs) on the interim text after the pause and on the final, before anything is sent (`onStopCommand`; also while a turn runs): "stop microphone", "stop the mic", "mic off", "turn off the microphone", "close the mic", "stop listening", "that's all", "oprește microfonul", "stop microfon", "închide microfonul", "gata cu microfonul", "nu mai asculta" and variants; words are matched with a small edit distance (recognizer typos). The microphone goes off and the app confirms ("Microphone off." / "Am oprit microfonul."); nothing reaches the chat. Typed, the same phrases are `ui.shell` commands (the `lang.mic.off` phrase group in `lang.common`, `ui.listening off`; "be quiet" and "taci" stop the voice output, not the microphone; there is no voice command that switches the microphone on; Romanian frames in `phrases.commands.ro-en.mjs`).
- **Phrase log.** A spoken message's record has `endType` (`final` | `pause-plausible` | `pause-timeout` | `mic-stop`) and `waitMs`; the export carries both.
- **Tests.** `scripts/test-webchat-voice.mjs` (headless Chrome with a fake `SpeechRecognition` that streams interim events with timings; `tests/webchat-voice.test.mjs` runs it when `PUPPETEER_CORE` is set) and Node unit tests of the detector in `tests/speech-endturn.test.mjs`.

### Spoken messages: phones, several tabs, room talk (FREEZE, MOBILE-VOICE, NOISE)
Implemented in `docs/webchat/ui/speech.mjs`, `docs/webchat/ui/voice-noise.mjs` and `docs/webchat/app.mjs`; tests `tests/voice-mobile.test.mjs` and `scripts/test-webchat-voice.mjs --only mobile,persist,twotabs,noise`.
- **The listening state is never persisted.** Every page load starts with the microphone off; a saved `handsFree` is migrated to `false` and never written. Only a click turns the mic on.
- **One recognizer per page.** The `SpeechRecognition` object is created once and reused (handlers of an older start are detached, events carry a session id); restarts are capped at 30 a minute, then the mic pauses with a visible reason. `aborted` (when not our own abort) and `audio-capture` count as failures, so the backoff applies.
- **One microphone for all tabs.** `createMicLock` (`navigator.locks`, plus a `BroadcastChannel` that tells the old owner it lost the mic; the channel alone when there are no locks). A second tab does not listen: the chat shows "The microphone is in use in another tab — use it here?" with a button, and takes over only on that click.
- **Hidden tabs.** `visibilitychange` hidden: recognition and speech stop and the lock is released; visible again it resumes only if the mic was on. `pagehide` releases everything; nothing resumes by itself.
- **No listening while working.** From the send until the turn, its effects and the spoken answer have finished the mic is paused ("working…", `data-mic="working"`) and then resumes by itself. There is no voice queue: a late final leaves its text in the box; typed text is sent with Enter.
- **One utterance = one message.** Android returns growing prefixes as separate finals. In that mode (`cumulative`, switched on by a mobile user agent or as soon as a final extends or repeats the previous one, or the result list holds several finals) a final waits `finalSettleMs` (700 ms) and replaces the pending text when it extends, contains or repeats it (otherwise it is appended); the end-of-turn rules then decide. The recognition session is restarted after each send (the result list is reset).
- **Filters before a send.** Fragment filter: a one- or two-word text made only of articles, pronouns, fillers and the like is dropped unless it answers an open question, is a game move, a number or a known command (`stop`, `undo`, `help`, `next` ...). Duplicate filter: a message within 10 s whose normalised edit distance to a sent one is at most 0.2, or that is a prefix or suffix of it, is dropped. Rate guard: at most one voice message per 2 s. More than 4 dropped messages in 10 s pause the mic with "I am hearing fragments — tap the mic to continue".
- **No action from noise.** A voice turn does not veil the tabs while it only thinks; a not-understood voice reply never applies state (no tab switch), and repeated not-understood voice replies within 20 s collapse into one (with a count).
- **Dry run.** At most one in flight; it gets an `AbortSignal` and a newer text aborts it; skipped for texts of more than 25 words; off on slow devices (`measureSpeed` above 45 ms, or two missed deadlines): the browser final and the text's plausibility decide.
- **NOISE.** A voice message with no complete reading, no world word (or a long text with only a stray one) and no direct address ("PSys2", "robotule") is ignored: shown greyed "ignored (not a command)" with "tap to send anyway", phrase log status `ignored`. Typed messages are never ignored; questions to the assistant ("what can I say?", "ce pot să zic?"), understood-but-unsupported messages and messages the dry run cannot judge pass. Settings › Voice: "Only respond when I say PSys2 / robotule" (`wakeWord`) ignores every message without an address.

### Settings modal (SET)
The settings are a full-screen modal dialog (`role="dialog"`, `aria-modal="true"`, hosted in `<body>` so that "full screen" is the viewport), opened only from the gear button in the header and by `ui.shell` commands, with a header (title "Settings", an x close button on the right) and a horizontally scrollable `role="tablist"` with one tab per topic. Changes apply at once, as before.
- **Tabs.** Understanding (formalizer, accept refused parses, spellcheck, simplify phrasing, fast path, edit head, partial understanding, best effort); Language (language, translation, language hint); Voice (English variant en-US / en-GB when English is selected, voice and its note, speech rate, hands-free mode, read answers aloud); Phrase log (keep a log, include button presses, filter, list, export JSON, clear); Models (status of the dispatcher and the normalizer: model, version, size, loaded / not loaded / "loads when needed", cache state, a Load now button each, the browser storage in use and a button that removes the cached model files); Developer (trace of every answer, per-stage timing overlay `showPerf`, build information from `build-info.json`); About (version and build, the AGPL-3.0 licence with the source link, credits of the vendored libraries and models with their licences, from `ui/about.mjs`).
- **Closing and focus.** Closes with the x button, Esc and the browser/phone Back button: opening pushes one history entry (`#settings/<tab>`), Back pops it, the x button and Esc pop it with `history.back()`. While open, the chat and the tool pane are `inert` and Tab wraps inside the modal; closing returns focus to the gear. The last tab is remembered (`psys2.webchat.settingsTab`).
- **Deep links.** `#settings/<tab>` (tab ids `understanding`, `language`, `voice`, `phrases`, `models`, `developer`, `about`), on page load and on hash change.
- **Commands.** `ui.shell` operation `ui.settings { what: open | close, tab? }` ("open settings", "open the voice settings", "open settings for models", "close settings") emits the host effect `settings { action, tab }`; "show my phrase log" (`ui.phraseLog show`) opens the Phrase log tab.
- **Tests.** `scripts/test-webchat-ui.mjs --only settings` (headless Chrome, 390x844 and 1280x800; `tests/webchat-ui.test.mjs` runs it when `PUPPETEER_CORE` is set): open and close with x, Esc and Back, every tab renders its controls, every checkbox saves, deep links, commands, 0 console errors, one screenshot per tab in `docs/webchat/screenshots/`.

### What PSys2 says it is (DOC)
The wording is fixed in one place per surface and checked by `scripts/test-webchat-ui.mjs --only doc`: greeting ("Hi, I am PSys2, a neurosymbolic assistant that runs entirely in your browser. ..."), header line ("neurosymbolic · runs in your browser"), `<title>`/meta description, Settings, About (`docs/webchat/ui/about.mjs`: what it is, what neurosymbolic means here, why the symbolic layer makes it safe, live model versions, measured accuracy from `training/RESULTS.md`, licence, credits) and the `ui.help` operation `ui.helpIdentity { what: what | how | ai | llm }` ("what are you?", "how do you work?", "are you an AI?", "do you use ChatGPT?"; it replaces the avatar's bare "what are you", which stays reachable as "which character are you").
