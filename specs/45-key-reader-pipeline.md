# Source cutter and request-key reader orchestration

`createKeyReaderPipeline` composes injected `cutter.cut(text)` and `reader.read(exactSubstring, {area, context})` providers into the existing canonical raw bridge and typed decoder. The application-facing method remains `propose(text)`; annotations, expected field identities and fixed field queries are not arguments. `getContext()` is a trusted host callback supplying only actual area and declared world context. Nested context authenticity belongs to that host boundary; this scaffold cannot establish truth of arbitrary supplied context. No grammar or sentence-pattern fallback exists.

Both provider envelopes are agreed with their trainer owners. Cutter output contains exact source text/unit, ordered nonoverlapping scalar spans, coverage, unresolved diagnostics and model identity. Request output contains exact substring source, one raw request, explicit relative path/range metadata, coverage, unresolved diagnostics and model identity. Each model identity includes checkpoint SHA, tokenizer SHA, codec SHA and decoder version. The factory verifies exact binding JSON bytes and hashes the two model identities plus binding hash into composite provenance. These identities are deployment assertions about injected providers, not attestation that arbitrary JavaScript computed a model output.

All cutter spans are checked before request-local reads. The cutter supplies the outer request span; conflicting local span text refuses. Every declared range must point to an owned string field whose exact scalar slice matches, then is lifted by the cut's scalar start. Nothing infers offsets from names such as `value_span`. The existing raw bridge retains canonical source bindings and value-normalization requirements. Unknown keys, fields, model identities, overflow, incomplete coverage or unresolved outputs prevent all candidates from being offered. Partial predictions cannot become executable. Multiple cut requests retain distinct source ranges, but absent dependency semantics still produce the existing unresolved dependency diagnostic: ordering cuts does not establish execution order or parallelism.

`budget` bounds orchestration work and independently bounds bridge work; `decoderBudget` is a separate decoder allowance. These are separate caps, not a claim that one shared counter measures neural computation. `maxRequests` limits local calls to at most 32; every input/output copy has an independent four-megabyte maximum, and source length is separately capped. Injected neural providers must enforce their own compute limits. Caller-supplied context snapshots are copied before provider calls.

The scaffold always reports `executable:false` and `graphConfidence:null`. It does not combine confidence products, invent a calibrated gate, install a provider into the app, or execute tools. Tests use explicitly injected generated toy outputs only. A future deployment needs frozen actual cutter and request-reader inference plus independent complete-pipeline semantic calibration; structurally valid graphs and complete model coverage flags do not prove correct understanding.
