# Offline predicted-request input preparation

`training/sop-bert/prepare-predicted-key-inputs.py` joins three independent inputs: original `id/text` source rows, frozen actual cutter prediction rows, and trusted actual host `id/area/context` records. The cutter run manifest must be complete and bind the exact source file and prediction output hashes. Its own hash and the context file hash are explicitly supplied. Every source ID must occur exactly once in all three files. Extra fields, including teacher annotations, are rejected at these record boundaries. Context truth remains a caller responsibility; hashing does not prove that invented or teacher-derived context is actual host state.

The builder follows the runtime pipeline's cutter-envelope rules: exact source snapshot and model identity, complete untruncated coverage, no unresolved issue, and at most 32 ordered, nonoverlapping Unicode-scalar intervals. It validates an entire message before producing any local request input. A later invalid interval cannot leave earlier partial requests eligible. Missing, overlapping, malformed or incomplete cuts remain refused with reasons. A complete all-O prediction is explicitly empty, not counted as correct understanding.

For each admitted interval the output contains exactly `id/text/area/context`, directly consumable by `predict-key-reader.py`. The text is the actual predicted substring, including supplementary Unicode characters at scalar boundaries. A separate origins ledger preserves source ID, cut index, global scalar range, source-text hash and cutter provenance. JSON-tuple cut identities avoid separator collisions. Multiple cuts remain available for offline per-request model measurement, while their message records retain `request-dependencies-unknown`; array order does not establish execution order.

The output directory is created exclusively and contains inputs, origins, message refusals/empty results, and a final manifest with hashes and all-record denominators. Source files are rechecked before publication. Without a complete final manifest, partial files are not trusted. The builder does not invoke a model, read a live checkpoint, run a GPU, inspect gold cuts, or admit effects. A downstream runner must retain this ledger when lifting predicted per-request field ranges back to the original message and must still validate the per-key checkpoint independently.

The current per-key CLI also emits static support diagnostics in its coverage record. A future runtime provider adapter must validate those against the frozen configuration and retain them as diagnostics, then pass only the known complete/truncated flags into the runtime pipeline's closed provider envelope. It cannot silently strip unsupported positive routes or convert static model support into whole-graph confidence. Neither that provider installation nor inference from an active training file is part of this preparation.
