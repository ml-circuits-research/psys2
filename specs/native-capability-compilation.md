# Capability compilation for native tools

The nonspatial path for a single-target imperative request compiles the existing `std.request`
graph with a `std.capability.context`. PSys2 supplies its active host's operation and parameter
declarations, canonical bindings, and a complete versioned observation as SOP facts in the
receiving world. The context references that trusted scope. The request carries no tool,
policy or observation declarations.

The library selects compatible live objects and ranks native calls by the result conditions they
can apply. The typed result identifies the selected object and its observed source, ranks alternatives,
names covered graph nodes and skipped conditions, and retains the actual policy and binding records
used. Scoped focus and recency resolve competing compatible objects. Argument defaults and
guards are supplied by the application's owned SOP policy. Native operation metadata supplies
required parameters and declared argument sources.

The document overwrite guard derives its occupied signal from a nonempty title or an observed
block or section. The meeting guard requires full scheduling coverage before dispatch. The compiler
retains defaults from the existing execution-policy world, including the observed clock and ordered
list values. The adapter checks readiness of declared knowledge dependencies, rechecks the same
instance, version and target incarnation, and translates the selected call into the shared exact
native SOP dispatch. Its concrete receipt and independently observed state determine the outcome.

The spatial request hook runs through the spatial compiler. Query and graph structures outside
this capability contract retain their existing handling. The change does not alter the learned
reader, its confidence policy or native editor undo history.

A degree word on a result ("a big sun", "make the house bigger") compiles through the library's
degree values. The capability policy derives `std.capability.degree` facts from the catalog's scale of size
(`k.expect.scale` step and `size_factor`, declared by an `app.execution.values` row with `codec=degree`) and
binds observed numeric properties such as Drawing's size with `app.execution.observedMeasure`. For an
existing target the factor multiplies its observed value. For a new object the adapter first compiles
without the unresolved degree, previews that call on a copy of the state through the host's `preview`
(with the knowledge its arguments name loaded), and records the created object's observations as
`app.execution.preview` facts. The policy turns those into `std.capability.base` for the parameters their
properties bind, so the degree scales exactly the value the area would otherwise give (its knowledge size
class). An unknown word, an ambiguous scale or a missing base leaves the condition skipped and reported.

A comparative without a number ("make the house bigger", "make it smaller") reaches the reader as
`operator=delta step=more|less`. The declared comparative projection
(`worlds/app.project/comparative-projection.sop`, evaluated once by `src/dialog/comparative-projection.mjs`)
derives `app.execution.comparativeFactor concept step factor` for each concept whose degree values come from
`k.expect.scale`: a step moves `offset` places from the `default` step (the catalog: "bigger" moves one step up),
and its factor is that step's `size_factor` over the default's (currently more 1.4, less 0.7). The raw-structure
bridge turns such a condition into `operator=factor baseline=before anchor=<concept> value=<factor>`, the library's
change relative to the observed value; a step on a concept without a declared scale, or a step with a measured
amount (`measure`, `unit`), stays an unresolved decision. Open: an absolute degree on an existing target
("make the house big") still multiplies the observed value, because the library's degree base for a selected
target is its observed value; it should use the kind's base (a library change).

## Authority for a native interface

Each editor owns `worlds/<editor>/native-interface.sop`. It declares the same
`std.capability.operation` and `std.capability.parameter` records used by the
compiler. Typed children retain structured values, argument metadata, effect scope,
coordinates, defaults and samples. A mechanical decoder builds the native argument
interface and attaches the scoped facts to live compilation. Avatar catalog choices
and Diagram color values enter as named runtime inputs. The composition clause in
Diagram includes Chart operations from the Chart interface, with a shared history.

`native-interface-source.mjs` transports the authored bytes into the Node and browser
modules. Generate or verify it with `node scripts/build-native-interfaces.mjs` or
`node scripts/build-native-interfaces.mjs --check`. The demo loader exposes the
authored sources directly in Worlds. Each existing `operations.sop` is the separate
legacy `core.operation` surface of the older world loader.

The natural-language reader receives the previous natural-language turn when it is available. An authored SOP request stays in the execution journal and contributes current native observations through its effects. Its serialized graph is excluded from the text reader's previous-utterance field.

The tool receives two SOP texts. The first is the concrete command. A compiled capability sends its selected `std.capability.call` and the argument wires reachable from that call. A manual control can send its compact operation wire or its declared structured argument circuit. The second text carries the invocation identity and observed revision. For example, `@invoke app.control.invocation id="move-9" version="3"` binds one attempt to that revision. Retries reuse the identity. The interpreter checks its operation declaration, decodes typed arguments and stages its native change. A caller can inspect the exact input on the response and in the Worlds activity record.

For spatial compilation the renderer measures a proposed constructor without committing it. Drawing and Diagram receive the constructor as SOP and return its native bounds. After dispatch, the response's tool call uses the exact command recorded by the interpreter, including its original wire ID.

The reference policy matches a contextual reading and live object bindings in a temporary world. A current reference uses the declared focus and recency criteria. Retargeting a previous change makes the prior focus ineligible and inherits that change only while its recorded state still matches. The Worlds activity record includes measured candidates and the choice circuit. The reference schema and the knowledge rules are separately inspectable.

Incomplete creation readings with a grounded trigger join the predicted target to
declared native constructors. The application measures bounded lexical distance,
reader-type mismatch and family-default mismatch. The authored creation policy
orders those measurements using the generic SOP choice compiler. Its input and
assessments are retained, and equally ranked canonical readings are compared
against the same live tool capabilities before one action can run.

A result span with a declared name role can supply a new target's name when the
chosen operation accepts names. The exact source range is required even when
the same noun appears elsewhere. Kind-role evidence coextensive with a bound
target noun is consumed once. Independently anchored requirements retain their
own constraints or appear in the execution's unapplied details. Undo records
the single committed circuit.

The interpreter routing policy admits the actual request graph into an isolated
World. A request selects history when the history compiler declares its act.
A relation constraint selects spatial compilation when it belongs to the
request and identifies a distinct subject and anchor. An ordinary request
selects the declared capability compiler. A failed placement keeps its
original diagnostic and does not reach another interpreter. Worlds records the
fired rule, its evidence and the selected interpreter separately from the
compiler's result.

Reader alternatives with a shared comparison implementation compile against
the same live snapshot. When an interpretation uses a different interpreter,
the comparison retains that interpretation and records the missing common
comparison explicitly. A compatible capability alternative can still supply
a compiled plan. Comparing proposals never invokes an editor tool.

An authored inspector request may own count, existence, members and values
projections. The query interpreter reads one detached observation of the
active native editor. It gives the library the same declared identity and
property evidence used for selectors. The library returns the answer and
observed scope in SOP with no tool call. Chat displays the answer and leaves
the board, previous action and Undo journal untouched. A complete empty
population yields zero or false. Incomplete observations can establish
witnessed existence and otherwise report the unsupported projection.

The frozen reader can supply a question projection and typed constraints without
emitting a complete request graph. A separate SOP policy resolves those heads
into read-only projections. Kind evidence must have an exact reader-supplied
source span. If several declared observable kinds are plausible, the library
compares their bounded lexical distances and retains the alternatives. The
query policy requires a separately grounded property key for a property
answer. An ambiguous membership cue or an absent key can leave a question
unanswered even when its target is recognizable.
