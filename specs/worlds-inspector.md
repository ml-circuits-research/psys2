# Global Worlds inspector

The Worlds application tab replaces per-editor Active/Code subtabs. It projects the actual worker registry, loaded SOP files, catalog declarations and files read, native host bindings, instance archives, native state properties and loaded semantic Worlds. Browser persistence, training pairs and message history are separate JavaScript nodes. The graph is a read-only inspection projection. Its central Application project World is an actual typed SOP registry used by runtime tab-to-domain resolution; the viewer also shows the JavaScript mechanisms around it.

Nodes expose their implementation, exact available source/declarations, tool capabilities and runtime data. Directed edges name the relationship supplied by the runtime. Available declarations and loaded sources remain distinct. Calendar owns canonical SOP state; the other four editors still own native JavaScript state, explicitly identified as their current authority; a serialized archive or cache must not be presented as an independent reasoning mechanism. Every native top-level state property, including undo and redo, remains inspectable. Search highlights nodes without deleting runtime data. The map has exactly two navigation levels: all real icon nodes and their labelled edges, then a detail page with Back/Forward history. Five horizontal layers show the central project and general mechanisms, main domains, domain instances/native companion structures, knowledge, and schemas. Domain columns follow explicit ownership; shared/unassigned records remain visible. Pan and zoom preserve the map position while visiting details.

The worker publishes `world-activity` events on the existing engine event channel. Each event carries a worker-local id, timestamp, node identities, phase and actual operation or stage. Instrumented boundaries include actual world loading, knowledge file reads, reader calls, session stages and native host invocation. Uninstrumented inner reasoning cannot be inferred from imports or world availability. The view pulses matching nodes and retains a bounded, explicitly counted event list with full event payloads. Inspection itself must not fabricate activation.

Instance snapshots use the library compact typed serializer while restoring legacy archives. Ordinary semantic scalar properties remain inline on object facts. The generic lossless native projection uses direct typed literals inside container nodes rather than separate scalar nodes; record fields use field.<key> attributes, ordered sequences use repeated item values, scalar roots remain literals, and reversible escaping retains arbitrary keys. Container references preserve nesting. This reduces transport serialization, without claiming to have removed the native state adapter or migrated its decisions into SOP worlds.

Validation includes real Chromium graph selection, exact archive display/copy, native history inspection, live native events, desktop layout and the existing full new-engine gate. Model retraining remains deferred until owner UI review.

## Explicit work files and model cache

Editor work starts fresh on navigation. There is no automatic native state restore, autosave, legacy JSON migration or startup archive conversion. The UI offers explicit Save work/Open work files and current-world SOP export. Work files declare the exact application build; another build is refused before any state adoption without conversion. Old browser databases remain untouched and inactive. UI training pairs remain session-local until downloaded. Settings and message logs retain their existing independent purpose and do not restore editor worlds.

SOP-BERT artifact bytes use their own SHA-256 keyed CacheStorage. Every cache read checks size/digest; corrupt entries are evicted and fetched again. Unavailable CacheStorage falls through to the authenticated fetch path. Only successful full reader assembly prunes this cache to current artifact hashes. This cache survives unrelated UI builds when weights are unchanged. Worlds exposes cache statistics separately from editor state and explicit snapshot buffers. ONNX sessions and WASM initialization still occur after navigation.


## Map and detail navigation

The architecture has exactly two presentation levels. The first is a complete map of actual nodes and labeled relationships: compact colored icons, short optional captions, hover names, pan/zoom and horizontal scrolling. Layout groups identify display categories and never create additional SOP worlds or imply semantic containment. The second is a large detail page with separate Overview, Properties, SOP Lang, Tools, Connections and Raw record views. Connection navigation retains Back/Forward history; returning to the map preserves its zoom and position. No permanent narrow inspector compresses the map.

Book terminology follows `soplang-words-lib/books/sop-worlds-teorie.md` version49 §5.1/5.3: world pattern, knowledge base and world instance; schema declarations are the rule portion, not automatically another independent world. Application loader packages may mix declarations, methods and initial facts. A catalog entry that does not declare its role stays a published SOP world. Import, package association and object references retain different relation labels. Native tool hosts disclose their combined JavaScript adapter/interpreter responsibility.

Settings is an inline application tab. The order is Drawing, Diagram, Calendar, Documents, Avatar, separator, Settings, Worlds; all tabs have icons. Opening utility tabs preserves the last editor context so actual commands and their activity can be observed while the map remains open.

The graph also exposes the independent static execution knowledge snapshot, both lazy execution World caches (loaded status read without initializing them), and retained SOP evidence worlds in `newEngineJournal`. Their actual source pins remain separate from the active catalog pin; telemetry is not relabeled as a justification trace.

## Declared runtime composition and help

The browser builds seven application packages: core, ui.shell and the five editor domains. Old kids, games, maps, arithmetic and standalone Charts packages are absent from this deployed composition. Chart primitives remain dependencies of Diagram tools. Profiles declare host factories, initializers, schemaWorld and exact schemaFiles. Generated native-interface.sop is derived from complete actual host bindings and stores structured metadata as standard typed SOP records/sequences, with parameter-to-operation references; it does not embed JSON strings. Four interfaces declare tools without claiming a complete state schema. Calendar additionally has a complete canonical instance schema.

The actual project registry is governed by worlds/app.project/instance-schema.sop. Main domains link to the schema identifier supplied by the composition. Sources in detail pages remain exact; source-derived type/key/tool summaries are inspection aids, not invented declarations or proof of neural NL coverage. JavaScript implementation metadata stays explicitly separate and inspectable.

Reader installation runs concurrently with UI boot. Text operations await the same reader initialization promise; concrete UI tool operations do not await model bytes. Schema validation, native semantics and their remaining migration limits stay visible in the architecture help. No retraining is part of this delivery.
