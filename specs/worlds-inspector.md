# Global Worlds inspector

The Worlds application tab replaces per-editor Active/Code subtabs. It projects the actual worker registry, loaded SOP files, catalog declarations and files read, native host bindings, instance archives, native state properties and loaded semantic Worlds. Browser persistence, training pairs and message history are separate JavaScript nodes. The graph is a read-only inspection projection. Its central Application project World is an actual typed SOP registry used by runtime tab-to-domain resolution; the viewer also shows the JavaScript mechanisms around it.

Nodes expose their implementation, exact available source/declarations, tool capabilities and runtime data. Directed edges name the relationship supplied by the runtime. Available declarations and loaded sources remain distinct. All five editors own canonical SOP content. Diagram stores nodes, groups, connections and chart data under its authored instance schema. Closed named joins identify current connection endpoints and linked chart sources. The inspector identifies each editor’s current authority and shows its actual observations. Every native top-level state property, including undo and redo, remains inspectable. Search highlights nodes without deleting runtime data. The map has exactly two navigation levels: all real icon nodes and their labelled edges, then inline detail subpages with direct ancestor breadcrumbs. Five horizontal layers show the central project and general mechanisms, main domains, domain instances/native companion structures, knowledge, and schemas. Domain columns follow explicit ownership; shared/unassigned records remain visible. Pan and zoom preserve the map position while visiting details.

The worker publishes `world-activity` events on the existing engine event channel. Each event carries a worker-local id, timestamp, node identities, phase and actual operation or stage. Instrumented boundaries include actual world loading, knowledge file reads, reader calls, session stages and native host invocation. Uninstrumented inner reasoning cannot be inferred from imports or world availability. The view pulses matching nodes and retains a bounded, explicitly counted event list with full event payloads. Inspection itself must not fabricate activation. A suggestion probe runs on a cloned host; its events carry `purpose: "suggestion probe"` and a `sample:` request id, are never attributed to a turn, and do not trigger a map refresh.

Instance snapshots use the library compact typed serializer. The library can decode legacy archives losslessly; application adoption still rejects incompatible build or knowledge pins without an implicit migration. Ordinary semantic scalar properties remain inline on object facts. The generic lossless native projection uses direct typed literals inside container nodes rather than separate scalar nodes; record fields use field.<key> attributes, ordered sequences use repeated item values, scalar roots remain literals, and reversible escaping retains arbitrary keys. Container references preserve nesting. This reduces transport serialization, without claiming to have removed the native state adapter or migrated its decisions into SOP worlds.

Validation includes real Chromium graph selection, exact archive display/copy, native history inspection, live native events, desktop layout and the existing full new-engine gate. Model retraining remains deferred until owner UI review.

## Explicit work files and model cache

Editor work starts fresh on navigation. There is no automatic native state restore, autosave, legacy JSON migration or startup archive conversion. The UI offers explicit Save work/Open work files and current-world SOP export. Work files declare the exact application build; another build is refused before any state adoption without conversion. Drawing, Diagram and Documents work files retain editor history and selection in a separate typed runtime record tied to the same instance and revision. The current-world SOP export contains the document, ordered blocks and text containers, source identities and marks. The editor computes its view and word counts from that content. Old browser databases remain untouched and inactive. UI training pairs remain session-local until downloaded. Settings and message logs retain their existing independent purpose and do not restore editor worlds.

SOP-BERT artifact bytes use their own SHA-256 keyed CacheStorage. Every cache read checks size/digest; corrupt entries are evicted and fetched again. Unavailable CacheStorage falls through to the authenticated fetch path. Only successful full reader assembly prunes this cache to current artifact hashes. This cache survives unrelated UI builds when weights are unchanged. Worlds exposes cache statistics separately from editor state and explicit snapshot buffers. ONNX sessions and WASM initialization still occur after navigation.


## Map and detail navigation

The architecture has exactly two presentation levels. The first is a map of actual records: one glyph and a plain-words caption per shown record, laid out in the Worlds pane's own pixels so that layers (rows) and tab columns stretch over the whole width and height; a resize lays it out again and fits it. Layout groups identify display categories and never create additional SOP worlds. A record declared as part of another (`partOf`), or a schema or source file used by exactly one knowledge World, is listed inside that owner's details instead of drawn separately; activity on such a part lights its owner. Relationship lines stay hidden until a record is pointed at (with the relationship names) or All links is pressed; lines at hubs with more than ten links stay faint even then. The second is an inline subpage inside Worlds with separate Overview, Properties, SOP Lang, Tools, Connections and Raw record views. It never uses a modal dialog, overlay, inert application region or focus trap; chat and application tabs remain usable. Connection navigation extends the breadcrumb ancestry; its first crumb returns to the map with its zoom and position preserved. No permanent narrow inspector compresses the map.

Book terminology follows `soplang-words-lib/books/sop-worlds-teorie.md` version49 §5.1/5.3: world pattern, knowledge base and world instance; schema declarations are the rule portion, not automatically another independent world. Application loader packages may mix declarations, methods and initial facts. A catalog entry that does not declare its role stays a published SOP world. Import, package association and object references retain different relation labels. Native tool hosts disclose their combined JavaScript adapter/interpreter responsibility.

Settings is an inline application tab. The order is Drawing, Diagram, Calendar, Documents, Avatar, separator, Settings, Worlds; all tabs have icons. Opening utility tabs preserves the last editor context so actual commands and their activity can be observed while the map remains open.

The graph also exposes the independent static execution knowledge snapshot, both lazy execution World caches (loaded status read without initializing them), and retained SOP evidence worlds in `newEngineJournal`. Their actual source pins remain separate from the active catalog pin; telemetry is not relabeled as a justification trace.

## Declared runtime composition and help

The browser builds seven application packages: core, ui.shell and the five editor domains. Old kids, games, maps, arithmetic and standalone Charts packages are absent from this deployed composition. Chart primitives remain dependencies of Diagram tools. Profiles declare host factories, initializers, schemaWorld and exact schemaFiles. Generated native-interface.sop is derived from complete actual host bindings and stores structured metadata as standard typed SOP records/sequences, with parameter-to-operation references; it does not embed JSON strings. Four interfaces declare tools without claiming a complete state schema. Calendar additionally has a complete canonical instance schema.

The actual project registry is governed by worlds/app.project/instance-schema.sop. Main domains link to the schema identifier supplied by the composition. Sources in detail pages remain exact; source-derived type/key/tool summaries are inspection aids, not invented declarations or proof of neural NL coverage. JavaScript implementation metadata stays explicitly separate and inspectable.

Reader installation runs concurrently with UI boot. Text operations await the same reader initialization promise; concrete UI tool operations do not await model bytes. Schema validation, native semantics and their remaining migration limits stay visible in the architecture help. No retraining is part of this delivery.

## Icon legend and readable component help

The map includes a collapsible legend that lists only the kinds of record present on the current map, each drawn by the same renderer as the nodes, with its count and a one-line meaning. **Colour is the primary cue.** Everything that is JavaScript is **one kind** (orange): tool hosts, interpreters, audited components, UI helpers, model runtime hosts and session data kept as JavaScript are not told apart, because the goal is to reduce and unify them; the only marker is badge **D** (domain logic in JavaScript). The trained reader (SOP-BERT and its binding bundle) has its own colour (purple) because it is not an SOP World. SOP Lang Worlds are told apart rigorously, one clearly different colour per kind in shades of their family: rules and policies in greens (tab rules, operational policy World, area registry World), instances in blues (instance World, execution evidence), knowledge in teals (catalog World, source or catalog file), schemas in greys (schema, tool interface declaration). The shape repeats the family as a secondary cue (hexagon: native; diamond: rules, policies and knowledge; circle: instances; square: schemas). Glyphs are large and filled; hollow means not used in this session. No two legend entries share a colour (tested).

Nonschema detail pages open Overview; records with a source-derived schemaView open Schema / legend, while schema source without that index opens SOP Lang. Overview presents supplied purpose, inputs, outputs, execution and limits before implementation metadata. Its optional contract is node.displayName and node.help {purpose, inputs, outputs, execution, limits}; missing interfaces are stated as undocumented rather than inferred from graph edges. Incoming/outgoing connections retain their declared relation labels and remain available in Connections. A concise display title never replaces the original full name or exact identity. Exact SOP sources and the explicitly separated JavaScript metadata remain available.

Cache objects are implementation metadata on their owner, not graph nodes. The reader retains authenticated artifact-cache statistics; execution modules retain their exact lazy source World and loaded/cache status in details. The tab registry World (`project:application`, formerly labelled Main World) is a concrete SOP instance of the tab registry schema (`app.project`): it records which tab shows which domain World and its current instance. It sits first in the Shared column of the instances layer; application tool packages remain explicitly distinct from current instance state.

Native tool boundary events carry a real invocation identity, validated arguments, expected version, monotonic invocation boundary duration, status and receipt metadata. The same observer wraps UI and declared-language tool calls without changing undo or verification policy. Full state snapshots are not duplicated into the event feed; current state, observations and journal data remain separately inspectable. Recorded animation time never replaces actual event time or duration.

## Map layers and interpreters

The map has five layers, top-down: **Native Layer** (all JavaScript as one kind, plus the trained reader), **Rules and policies (SOP)** (SOP Worlds that hold rules: each tab's SOP files with its area declaration and act rules, tool interface and instance schema, formerly called the tool package; the operational policies for interpretation, reader context and admission, routing, composition, creation, placement and scene defaults, history; the area registry World), **Instances** (live state SOP Worlds), **Knowledge** and **Schemas**; empty layers are omitted. No preferences World exists yet; `w.preferences` is planned, and "About this view" says so. There is no separate tools or session layer: JavaScript session data is native data and sits in the Native Layer. Columns are Shared by all tabs plus one per tab; a caption in a tab column drops the tab name the column header already shows. Each layer header has a "What is in this layer?" link that opens its description and the display names of its records.

- **Native Layer** lists each tab's tool host and the interpreters that actually run: the SOP area interpreter (`worlds/sop-area.mjs`, reads each tab's area.sop and builds its tool host), the SOP world host (`worlds/sop-world-host.mjs`, runs a command through the tab's authored rules and the library's generic acts), the placement compiler (std.problem; library `compileRequest`, called by `src/dialog/spatial-placement-execution.mjs`) and its two solvers, the SOP-BERT reader, request admission, the Session (turn coordinator), the world loader and the activity bus. A tool host links to the area interpreter and the world host when its composition lists those runtime modules, and the compiler links to every host that declares a spatial operation.
- **Search providers.** The internal search is always available. The Z3 node reads `src/dialog/placement-search-inspection.mjs`, which reads the provider's status accessor (`z3Status()`, exported as `placementSearchStatus`) and never loads or warms Z3 itself. Its caption shows the state (Z3 solver (not loaded / warming / ready / unavailable)); its details give what started it, base URL, z3-solver version and load time, or the reason it is unavailable. The compiler records which provider solved the last placement; placement activity events also name the compiler and that provider.
- **Instances** replaces the former Instances and session state layer. Now that every tab keeps its state as an SOP instance World, the instance Worlds (circles) are the five tab instances and the session undo/redo journal World (the area registry World is shown with the rules). Records still kept as JavaScript are in the Native Layer: the application shell state (`ui.shell`, the only world without an authoritative SOP state), the retained execution journal, chat and event history and UI training pairs. The world loader is JavaScript (Native Layer); session memory (message counter, conversational references, recent worlds, the undo/redo journal carrier, reader and placement settings) is `partOf` the Session and listed inside it, linked to the undo/redo World that holds the same journal facts. The layer description lists these records from the actual data.
- **Knowledge** holds the published catalog worlds (the operational SOP policy worlds are in SOP rules and declarations); each catalog World lists its source files (read or declared) inside it, and a policy lists the schema it alone imports.

## Recorded playback and exact activity log

The activity log records incoming evidence independently of visual playback. It retains the newest 300 deduplicated events, displays shown/retained/received counts and eviction explicitly, supports filtering and copying the complete retained window, and opens each original event with its exact payload and recorded node references. Runtime timestamps, monotonic durations, status, operation and errors remain distinct from animation timing. The full log subpage can be reopened without clearing its evidence.

Subscribed events enter the activity log. Animate on a chat response opens the Worlds map and queues only that response’s recorded stages. Each stage highlights the recorded nodes and their connecting edges for at least 500 ms. The playback controls appear during a requested animation. Leaving Worlds ends it. Refreshing the map or receiving new activity never starts it.

Detail navigation records node, tab, nested property path and collection page. Clickable breadcrumbs jump directly to any recorded node ancestor or nested property ancestor. The initial map crumb restores the same graph DOM, pan and zoom. Detail pages are ordinary regions inside Worlds, and changing editor/utility tabs remains available while reading them. Recorded playback and evidence ingestion continue independently while the map is hidden by an inline subpage.

Playback groups consecutive events only when their declared operation, stage, correlation, invocation and world identities agree. A group retains every event ID and the union of actual recorded node identities; its count and Stage details make that grouping explicit. In particular a burst of declared knowledge.read events is one visual stage rather than hundreds of half-second delays. Different correlations or invocations remain separate, chronology is preserved, and the Activity log retains every event unchanged.

## Overnight navigation, legend and replay visibility

The map legend is a collapsible vertical explanatory list overlaying the map's left edge, one row per symbol present on the map; it is not an icon-only strip and opening it does not re-layout the map. Detail and log fonts are larger, and the same +/- controls adjust font scale modestly as well as graph zoom. Breadcrumbs are the primary navigation: the first crumb always opens the initial Worlds map, and subsequent crumbs open node or arbitrary nested-property ancestors. Previous/Next and redundant Back-to-map buttons are removed. All subpages remain inline inside Worlds, leaving chat and application tabs usable.

Activity log is a full Worlds subpage opened by its navigation button; it is not a bottom panel on the map. Playback controls remain available on all Worlds subpages. Recording and retention continue independently from playback. Visual playback runs only when the Worlds tab is visible, the browser document is visible, and the document has focus. Losing document visibility/focus freezes the stage clock and resumes its remaining hold later. Manual Pause remains independent.

The component exposes replayEvents(eventsOrIDs) returning {accepted, missingIDs} and setVisible(boolean). Explicit reply replay preserves the supplied event order, performs no execution, and excludes unrelated live events from that playback queue while still recording them in the log. Objects can replay retained per-response evidence independently of the log ring; IDs resolve only against currently retained records and missing IDs are reported.


## Avatar state authority

Avatar, like Calendar, stores only an SOP carrier in the operational session. Its complete declared `instance-schema.sop` represents the current composition, owned slot records, role colours, explicit overrides, geometry, saved compositions, ordered undo/redo snapshots, options and referents. Scalars are direct values; references describe actual ownership. Native handlers and rendering receive temporary decoded data and successful transactions commit SOP facts. There is no retained parallel native face store. This changes storage authority, not the origin of every native semantic algorithm.

Current composition/slot facts explicitly bind their observed interface through `nativeType` and `id`; historical snapshots do not acquire a current native identity. Instance inspection follows these declared interface attributes and rejects missing/ambiguous/conflicting bindings. It does not pretend that the state schema type and tool observation type are identical. The full state schema/facts and native tool adapter remain visible separately.

## Implementation identity and purpose

Each map node carries authored `why` metadata and an explicit `representation`: SOP declarations/state, JavaScript/native implementation, model, or catalog metadata. Orange identifies JavaScript and its catalog records; green identifies SOP source/facts; blue identifies SOP-BERT. Role icons remain separate from implementation colours. Native adapters and application packages with native bindings do not acquire a SOP code tab because their description mentions SOP. Empty strings do not count as source. Why is the default page, with short purpose prose and flat navigation links; complete runtime metadata remains accessible separately.

All published catalog entries have source paths and concrete purpose comments grounded in their authored definitions. Catalog-only, inspected-only and source-read are different states; none proves reasoning participation. `k.interest` specifically has no active interest-scoring call in this demo: only its older schema occurs in the executor snapshot, without its scoring facts. This is a missing integration, not a working reasoning capability.

Catalog SOP text loads on explicit inspection of declared files, in bounded complete-file pages. Opening the architecture reads only the catalog index when necessary and skips preparing native knowledge services: an SOP area whose base this session has not prepared gets no tool host (creating one would read its knowledge and start its state); its instance node shows the facts it holds and says it was not prepared. An observed object of a prepared area binds to the instance facts its `app.observe.object` was derived from (the derivation's own support record), never to a value match. Opening the architecture preempts a running suggestion probe, as foreground actions do. Neither operation executes the inspected knowledge World's rules. Breadcrumbs, property navigation and relationship navigation are borderless links. The SOP tab displays exact available source, offers declared source loading, or is omitted when no SOP source is exposed; it never labels JavaScript/JSON as SOP Lang.

## Schema ownership and instance admission

Reusable schema definitions belong to their schema modules. Calendar and Avatar each import their declared schema into an adapter-owned base context, then fork that context for an instance read. The instance carrier contains only owned concrete facts and references; it cannot add types, slots, rules, rule patterns/templates, schema mappings or imports. Admission uses the library's `tell(..., {factsOnly:true})` option so rejection occurs before an instance input can alter schema ownership or evaluate injected rules. A failed read does not modify the reusable schema context or the original carrier.

The semantic World used for evaluation is a temporary composition of the imported schema and instance facts. Its matrix is not the persisted instance. Inspection and Save work serialize concrete facts, not the schema matrix. Evaluating a rule in a temporary context does not insert that rule or its deductions into editor storage. Knowledge imports remain separate declared dependencies rather than copied instance rows. Drawing, Diagram and Documents export their authoritative instance facts separately from the runtime history used by the editors.

Execution policies expose their authored facts separately from the imported `app.execution` and `app.request.composition` schemas. The inspector links each policy to its exact schema source rather than presenting the evaluation matrix as policy state. Execution value lookup is generated from the value-type contracts actually declared by those policies and area bindings. Its snapshot contains imports and knowledge facts; the schema module texts are held separately for replay. The generator records actual source ownership and follows the active catalog pin. A cached evaluation context is not an editor instance.

Catalog entries explicitly identify a vocabulary source through `vocabulary`. Structural lookup reads schema declarations from the schema source and lexical facts from that separate dependency; it does not infer ownership from a filename or concatenate them into a purported schema. The site copy carries vocabulary files declared by both knowledge and reusable-schema entries. Offline person and diagram profiles likewise retain separate structural schema and vocabulary fields, composing them only when their existing consumer evaluates a request. These profiles are not claims that those older consumers are the active SOP-BERT reader.

## JavaScript on the runtime path (generality audit)

Every JavaScript module that a chat turn or a UI action can run is declared in `src/dialog/runtime-component-registry.mjs`, grouped into components. The inspection (`inspectWorldsRuntime`) puts each component on the map: a component that names an existing record (`node`, e.g. `component:reasoner`, `component:reader`, `component:sop-area`, `interpreter:<world>`, `component:problem-compiler`, `component:library`, `runtime:registry`, `knowledge:catalog`) decorates that record when it is present; otherwise it is its own record in the **JavaScript on the runtime path** band, in its area's column when it declares `area`. UI helpers of the tabs (drawing renderer, diagram inspector, calendar, documents, avatar, chat shell, gesture quantization, speech, model hosts, browser persistence) are components too, marked `JavaScript UI helper`.

- Each component node carries `audit`: `badge` (`domain-logic` when any module makes a domain decision in JavaScript, otherwise `generic`), the module list with classification (`generic`, `domain-logic`, `data`, `sop-carrier`), generality impact, the decision, file:line evidence, the SOP/knowledge replacement and the **hidden behaviour** (silent retries, fallbacks, filters, defaults, thresholds and UI-side computations that do not appear in the trace or the activity log), `actsOn` (records it reads or changes) and `activity.operations`.
- The map draws only badge **D** (domain logic in JS) on the glyph; whether a component has an activity hook (and so can change a result without lighting up) is stated on its overview page with the audit table.
- Activity: a world-activity event lights the records in its `nodeIds` and every component whose registry entry declares the event's `operation`; the event page lists those emitters. Nothing else is inferred: components without an emitted operation stay dark even when they ran, which is why they carry the dashed ring.
- Links: `actsOn` entries whose target is in the base graph become edges; targets that only the merged worker graph holds (`execution:*`, `browser:*`, `project:*`) are returned as `componentLinks` and drawn by the explorer when both ends exist.
- The full audit with the top domain decisions and their replacements is `specs/js-generality-audit.md`.

## Stewardship of the Worlds map

The map must show the real system as the code changes. The steward (any agent changing the runtime) keeps it true mechanically:

1. `tests/worlds-component-registry-declared-host.test.mjs` walks the real module graph from `docs/webchat/app.mjs`, `docs/webchat/ui/engine-worker.mjs`, the tab modules in `docs/webchat/ui/tabs/index.json` and the declared world runtime modules (`runtimeModules`, `nativeHost`, `nativeInitializer` in `docs/webchat/worlds/index.json`), following static, dynamic (`import`, `vurl`, `imp`, `host.asset`) and `new URL(...)` imports, mapping `lib/X` to `src/X`. It fails when a reachable module is not registered, when a registered module is no longer reachable, when a domain-logic module has no file:line evidence or replacement, when a hidden behaviour has no file:line, and when a component has no node on the map.
2. When you add or move a runtime module: add it to the right component (or a new one) with its classification, decision, evidence, replacement and hidden behaviour; when it emits world-activity events, list their operations in the component's `activity`. When you remove one, remove its entry. Update `specs/js-generality-audit.md` when a domain decision appears, moves to SOP or disappears.
3. When you add an activity hook to a module, add the operation to its component so the map lights it; a component with no hook keeps its dashed ring.
4. Verify in the real page: `npm run build:webchat`, open the Worlds tab (the `scripts/lib/browser-reader-route.mjs` route), check the JavaScript band, badges and a turn's activity, and take a screenshot.
5. Reachable is not the same as executed in every turn: the registry lists what can run; activity events show what did run. `scripts/worlds-runtime-coverage.mjs [site] [out.json]` measures which registered modules execute during real turns (V8 precise coverage in the page and the worker); refresh the measured column of `specs/js-generality-audit.md` with it after large changes.

## Reader, boundary and limit records

The worker passes live records to the inspection: the reader's binding bundle summary (`engine.requestReader.bindings()`, summarised by `summarizeReaderBindings`: hash, catalog pin, sizes, key coverage per area with bound and unbound keys and reasons, kind lemma source worlds), the reader diagnostics of the last turn (cutter spans, key-reader packets, minimum probability, unresolved items, context fit), the turn limits (`LIMITS`, specs, step budget), the translation boundary record (calls, failures, last call and last failure reason) and the suggestion sampler record (runs, last run). They appear as `component:reader-bindings` (linked from the reader and to the `knowledge-world:*` records that supply kind lemmas), `runtime:reader-evidence`, `runtime:turn-limits`, `runtime:translation-boundary` and `runtime:suggestion-sampler`. Worker events: `reader.cut` (per-turn cut spans, lights the request cutter component), `translation.translate` / `translation.detect` (start, end, error), `suggestion.sample` (start, end with view and item count; probe events are marked as suggestion probes). A failed turn's `Session request failed` event carries the guard reason, the stage and the active limits. The worker and the page each retain the last 300 activity events. The map is a snapshot read between actions; "About this view" and the legend say so.
