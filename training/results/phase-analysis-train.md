# Phase analysis of the training data (does the whole pipeline close?)

Generated by `scripts/eval-phases.mjs` + `scripts/lib/phase-report.mjs` on 1500 sampled training items (1411 scored end to end, 89 needs_review items without a gold circuit), seed 7, 215 s on 20 workers. Raw data: `training/results/phase-analysis-train.json` (one row per item, with the per-phase trace) and `training/results/phase-analysis-operational.json` (the operational set through the same tracer).

## Method

Each item goes through the real dialog engine in the webchat configuration (dispatcher v2 int8 via onnxruntime-node, rule validation, spellcheck, partial understanding, acceptRefused; no normalizer, as in the rules/dispatcher evaluation). **Right** = the concatenated, id-normalized SOP of everything understood equals the concatenation of the gold segment SOPs (string values compared case-insensitively; negatives: nothing understood). In parallel an **oracle** runs the rule formalizer on the gold text with the gold world only, in a session seeded like the item, no dispatcher or validator. The first deviating phase of a wrong item is, in this order:

| Phase | Deviation test |
| --- | --- |
| P1 translation | not applicable: training data is English (counted only for non-ASCII Romanian text; tag G8) |
| P2 expansion | oracle fails on an item of the expansion families (self_correct, shared_arg, ellipsis, repeat_undo) or a marker text, with no data cause |
| P3 segmentation | no segmentation of the dispatcher beam (4) matches the gold pieces (char IoU >= 0.6) |
| P4 world proposal | in the matching segmentation a piece has no gold world in its top-3 |
| P5 rule formalizer | oracle (gold text, gold world) does not give the gold SOP; split into DATA (label noise) and SYSTEM (pattern missing / reads differently). A data cause is attributed here first, because the gold itself is untrustworthy |
| P6 validation | oracle is right, segmentation and world are available, but the validator chose another reading (reason: segmentation, world, variant) |
| P7 execution | SOP right but the interpreter reports execution_error / unknown_argument (state-dependent refusals such as precondition_failed are only counted) |
| P8 reply | SOP right but the reply holds an unrendered template, "Something went wrong" or nothing |
| discourse | the discourse layer answered instead of the dispatcher (not in the user's list; shown separately) |

The sample is stratified (not proportional): per-world train records by world x label status (rules-fail, rules-differ, generator-disagrees and negatives oversampled), paraphrase variants by label status x world (needs_review x4, rules-fail/differ x3), multi-command train by family x segment count x variant. Raw percentages therefore **understate** the real quality; every row carries a population weight and the "weighted" columns extrapolate to the pools (38574 per-world train records, 7369 paraphrase variants, 18000 multi-command train messages).)

Independent deviation counts (an item may deviate in several phases; not only the first): P3 2, P4 18, P5 236 (oracle differs from gold), P7 6, P8 0. The dispatcher (P3+P4) is almost never the first failure on the training data (P3 1, P4 9); the weak points are the rules (P5) and the validator accepting readings it should refuse (P6).

Tags of the worker task that would fix the wrong items: G1 (selection: complete before partial / generated) 3; G2 (self-corrections executed early) 1. Only a handful of training items are G-task failures: G1/G2/G3/G6/G8 are mostly operational-set problems (messy real input), not training-data problems.

## 4. Data problems versus system problems

DATA problems (the oracle shows the gold is wrong, independent of the dispatcher): **43 of 1411 scored items**, about **867 of 63943 training items (1.4%)** by population weighting. Everything else in the failure list is a SYSTEM problem.

| data problem | sample items | weighted population | label statuses | proposed fix |
| --- | --- | --- | --- | --- |
| gold_target_from_another_world | 26 | 687 | {"rules-own":15,"rules-fail":1,"clean":4,"rules-agree":1,"canonical-ok":1,"plain":3,"rules-differ":1} | relabel the SOP with the rule reading of the labelled world when it parses completely, otherwise mark `needs_review`; keep the text and world label for dispatcher training (the world label is right, the circuit is wrong) |
| label_says_rules_differ | 13 | 110 | {"generator-disagrees":6,"rules-differ":7} | relabel with the rules' reading when the text values agree with it (most cases); the remaining `rules-differ` records go to `needs_review`. Do not drop: the sentence is good dispatcher data |
| gold_value_not_in_text | 4 | 69 | {"clean":1,"rules-differ":1,"plain":2} | relabel from the text (regenerate the target from the edited text) or drop the SOP target; multicmd: regenerate the segment target after the text edit |

Highest-density source: label status `rules-own` (the target is the rule router's own reading over all worlds): 15/69 = 21.7% of the sampled rules-own items carry a circuit from another world. Population check on all 38574 per-world train records: 542 (1.4%) have a text that also occurs in another world with a different target (cross-world ambiguity; the label depends on the tab context).

Not data problems, although they look like it at first sight: `rules-fail` paraphrases (the label is the canonical circuit and is right; the rules cannot read the variant), and `generator-disagrees` records where the pipeline reproduces the gold (they are right in most cases: 89.7% of the sample).

Items whose gold is `negative` deserve a decision: 36 of 47 sampled negatives are accepted by the pipeline (P6 over-acceptance). That is a system problem, but `negation` records such as "I do not want a balloon" (gold: nothing) are parsed as `draw.remove` by the rules of the gold world, which is arguably a better answer than the label; those (`negative_parsed_by_rules`) are candidates for relabel.

Summary of the split on the wrong items (sample):

| class | wrong items | share |
| --- | --- | --- |
| DATA (wrong or inherited label) | 43 | 17.8% |
| SYSTEM | 198 | 82.2% |

Within SYSTEM, the largest block is missing rule coverage for colloquial variants (rule_unparsed + rule_partial_parse), followed by over-acceptance of negatives and cross-world ambiguity. No G task addresses the first block; the normalizer and new patterns do.

## 7. Reproduce

```
node scripts/eval-phases.mjs --ort <onnxruntime-node entry> --workers 20 --name train         # stratified train sample (--n 1500 --seed 7)
```

`--data-root` points at the training directory (the datasets are not tracked in git; the default falls back to the main checkout). Each worker holds one engine and one ONNX session with `intraOpNumThreads=1`.
